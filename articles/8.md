# Тема 08. Основы Vue 3: реактивность, компоненты, props/emits, жизненный цикл


## Аннотация

Vue 3 — прогрессивный фреймворк (progressive framework) для построения пользовательских интерфейсов, и в этой теме мы разберём его фундамент. Вы узнаете, как устроена реактивность (reactivity) на основе `Proxy`, почему компонент можно считать «функцией от состояния», и как данные и события текут между компонентами через props и emits. Отдельно разберём двустороннее связывание `v-model` и хуки жизненного цикла (lifecycle hooks) — точки, в которых можно «вклиниться» в жизнь компонента. Теория закрепляется практикой: мы начнём собирать прототип списка задач учебного проекта.

## Цель темы

**Цель:** освоить базовый синтаксис и реактивность Vue 3.

После изучения темы вы будете знать/уметь:

- знать, как система реактивности Vue 3 использует `Proxy` для отслеживания чтений и записей;
- знать различия между `ref` и `reactive`, Options API и Composition API;
- уметь создавать однофайловые компоненты (Single-File Component, SFC) в синтаксисе `<script setup>` с типизацией на TypeScript;
- уметь проектировать взаимодействие «родитель — ребёнок» через props, emits и `v-model`;
- уметь применять хуки жизненного цикла для работы с DOM и очистки ресурсов.

## Теоретическая часть

### 8.1. Реактивность на основе Proxy: как Vue «понимает», что данные изменились

Ключевая идея Vue: вы мутируете обычные данные, а фреймворк сам понимает, какие части интерфейса зависят от этих данных, и перерисовывает их. Никаких ручных вызовов «обнови экран» — этим занимается система реактивности (reactivity system).

Во Vue 3 она построена на прокси-объектах (Proxy) — механизме языка, позволяющем перехватывать операции над объектом: чтение свойства, запись, удаление, проверку наличия ключа. Упрощённо внутренний код выглядит так:

```ts
const target = { title: 'Написать конспект', done: false }

const state = new Proxy(target, {
  get(obj, key, receiver) {
    track(obj, key) // запомнить: «текущий эффект читает это свойство»
    return Reflect.get(obj, key, receiver)
  },
  set(obj, key, value, receiver) {
    const result = Reflect.set(obj, key, value, receiver)
    trigger(obj, key) // уведомить все эффекты, зависящие от свойства
    return result
  },
})
```

Работает это так:

1. **Сбор зависимостей (dependency tracking).** Когда компонент рендерится, его render-эффект (render effect) читает свойства состояния. Каждое чтение проходит через ловушку `get`, и Vue запоминает: «это свойство используется этим эффектом».
2. **Уведомление (trigger).** Запись в свойство проходит через ловушку `set`, и Vue ставит зависимые эффекты в очередь на перезапуск.
3. **Планирование (scheduling).** Обновления не выполняются синхронно на каждую мутацию. Vue накапливает их и применяет асинхронно, один раз за «тик», устраняя дубликаты. Если вы десять раз изменили одно и то же поле, компонент перерисуется один раз.

```ts
import { reactive } from 'vue'

const state = reactive({
  tasks: ['Написать конспект', 'Сдать лабораторную'],
  filter: 'все',
})

state.filter = 'активные' // интерфейс обновится сам, без «магии» вроде setState
```

Вложенные объекты оборачиваются лениво (lazily): проксирование происходит при первом обращении к вложенному полю, а не рекурсивно при создании. Это экономит память на больших структурах.

> 💡 Почему Vue 2 требовал `Vue.set`, а Vue 3 — нет? Vue 2 строил реактивность на `Object.defineProperty`, перехватывая каждое свойство отдельно, и не видел добавление новых свойств и запись по индексу массива. `Proxy` перехватывает объект целиком, поэтому `state.tasks.push(...)`, `delete state.filter` и `state.tasks[0] = ...` работают «из коробки».

> ⚠️ Частая ошибка: деструктуризация убивает реактивность. Если сделать `let { filter } = state`, переменная `filter` станет обычной строкой — копией значения, а не «проводом» к прокси. Изменения `filter` Vue не увидит. Нужны производные значения — используйте `computed` или `toRefs`.

### 8.2. `ref` и `reactive`: два способа завести реактивное состояние

Vue предоставляет два API для создания реактивных данных.

**`ref(value)`** оборачивает значение в объект с единственным свойством `.value`. При чтении/записи `.value` срабатывают те же механизмы track/trigger:

```ts
import { ref } from 'vue'

const count = ref(0)          // Ref<number>
count.value += 1              // в коде — только через .value

const task = ref({ title: 'Новая задача' })
task.value.title = 'Исправить' // поля объекта тоже реактивные
```

**`reactive(obj)`** сразу возвращает прокси вокруг объекта — без `.value`:

```ts
import { reactive } from 'vue'

const draft = reactive({ title: '', description: '', deadline: '' })
draft.title = 'Подготовить доклад' // обращение напрямую
```

Сравним честно:

| Критерий | `ref` | `reactive` |
|---|---|---|
| Что хранит | примитивы и объекты | только объекты (object / array / Map / Set) |
| Доступ к значению | через `.value` | напрямую |
| Переприсваивание | `count.value = 5` — работает | `draft = {...}` — связь теряется (это уже другой объект) |
| Деструктуризация | не применяется | ломает реактивность |
| В шаблоне | авторазворачивается: `{{ count }}` | используется как есть |

> 💡 Практическое правило курса и, пожалуй, всего сообщества: **по умолчанию используйте `ref`**. Он одинаково работает с примитивами и объектами, переживает переприсваивание и не подкладывает сюрпризов при передаче в composables. `reactive` удобен для форм с множеством полей, пока вы не начнёте его деструктуризировать.

Отдельно существуют «неглубокие» варианты `shallowRef` и `shallowReactive` (реактивен только верхний уровень) — они пригодятся для больших структур, где глубокое отслеживание избыточно, а также `toRef`/`toRefs` для создания «живых ссылок» на поля реактивного объекта.

### 8.3. Options API против Composition API. Синтаксис `<script setup>`

Исторически компоненты Vue писались в **Options API**: конфигурация объекта с секциями `data`, `methods`, `computed`, `watch`, где всё склеивалось через `this`:

```vue
<script>
export default {
  data() {
    return { count: 0 }
  },
  computed: {
    doubled() {
      return this.count * 2
    },
  },
  methods: {
    increment() {
      this.count++
    },
  },
}
</script>
```

Проблема Options API проявляется на средних и больших компонентах: логика одной функциональности размазана по секциям («вот всё про фильтры в data, computed и methods, вперемешку с логикой пагинации»), а переиспользование логики требует миксинов (mixins), которые неявно подмешивают свойства и конфликтуют именами.

**Composition API** решает обе проблемы: логика описывается обычными функциями и переменными, которые можно свободно группировать по смыслу и выносить в переиспользуемые composables (этому посвящена тема 09). Тот же счётчик:

```vue
<script setup lang="ts">
import { ref, computed } from 'vue'

const count = ref(0)
const doubled = computed(() => count.value * 2)

function increment(): void {
  count.value++
}
</script>

<template>
  <button @click="increment">{{ count }} (удвоенное: {{ doubled }})</button>
</template>
```

`<script setup>` — compile-time-синтаксический сахар поверх Composition API:

- всё объявленное в блоке верхнего уровня автоматически доступно в шаблоне, никаких `return`;
- импортированные компоненты сразу регистрируются и доступны в шаблоне;
- `props`, `emits` и слоты объявляются макросами компилятора `defineProps`, `defineEmits`, `defineSlots`, `defineModel` — их не нужно импортировать;
- компилятор оптимизирует результат: меньше служебного кода, быстрее инициализация.

| Критерий | Options API | Composition API (`<script setup>`) |
|---|---|---|
| Организация кода | по секциям (`data`, `methods`…) | по функциональности |
| Переиспользование логики | миксины (mixins) | composables — обычные функции |
| Типизация TypeScript | удовлетворительная | отличная (обычный TS-код) |
| `this` | требуется | не используется |
| Когда уместен | маленькие примеры, учебные курсы | реальные проекты; стандарт курса |

> ⚠️ Смешивать API в одном компоненте можно, но незачем: в курсе и в проекте используется исключительно `<script setup>` + TypeScript.

### 8.4. Компоненты. Props: данные вниз

Компонент (component) — переиспользуемый кусок интерфейса со своим состоянием и шаблоном, однофайловый компонент `.vue` с секциями `<template>`, `<script setup>` и (опционально) `<style scoped>`.

Связь «родитель — ребёнок» строится на принципе **однонаправленного потока данных** (one-way data flow): родитель передаёт данные вниз через props, ребёнок никогда не мутирует их напрямую.

```vue
<!-- TaskItem.vue -->
<script setup lang="ts">
export interface Task {
  id: number
  title: string
  done: boolean
}

defineProps<{
  task: Task
}>()
</script>

<template>
  <li :class="{ done: task.done }">
    {{ task.title }}
  </li>
</template>
```

```vue
<!-- TaskList.vue -->
<script setup lang="ts">
import TaskItem, { type Task } from './TaskItem.vue'

defineProps<{
  tasks: Task[]
}>()
</script>

<template>
  <ul>
    <TaskItem v-for="task in tasks" :key="task.id" :task="task" />
  </ul>
</template>
```

Обратите внимание: `defineProps<{ tasks: Task[] }>()` — чистая типизация без рантайм-валидации; типы props компилятор выводит из дженерика. Значения по умолчанию задаются через `withDefaults`:

```ts
const props = withDefaults(
  defineProps<{
    tasks: Task[]
    showArchived?: boolean
  }>(),
  { showArchived: false },
)
```

> ⚠️ Частая ошибка: изменять prop внутри ребёнка («ну я только отсортирую массив, который мне передали…»). Vue выдаст предупреждение, а логика станет непредсказуемой: родитель не знает, что его данные «поправили». Нужна локальная копия — сделайте `computed` или `ref` с копией и работайте с ней.

### 8.5. Emits: события вверх

Если ребёнку нужно сообщить родителю о действии пользователя, он **эмитит событие** (emit) через макрос `defineEmits`. События — единственный штатный канал «снизу вверх».

```vue
<!-- TaskItem.vue -->
<script setup lang="ts">
defineProps<{ task: Task }>()

const emit = defineEmits<{
  toggle: [id: number]
  remove: [id: number]
}>()
</script>

<template>
  <li>
    <input
      type="checkbox"
      :checked="task.done"
      @change="emit('toggle', task.id)"
    />
    {{ task.title }}
    <button aria-label="Удалить задачу" @click="emit('remove', task.id)">✕</button>
  </li>
</template>
```

Родитель подписывается в шаблоне через `v-on` (`@`):

```vue
<TaskItem
  v-for="task in tasks"
  :key="task.id"
  :task="task"
  @toggle="toggleTask"
  @remove="removeTask"
/>
```

Правила хорошего тона:

- объявляйте события через типизированный `defineEmits<{...}>()` — TypeScript проверит имена и аргументы;
- имена событий в объявлении — camelCase, в шаблоне допустим kebab-case (`@update:model-value`);
- не выдумывайте события «на будущее»: событие — это факт, произошедший в компоненте (`toggle`, `remove`, `submit`), а не команда родителю.

### 8.6. `v-model`: двустороннее связывание

На нативных элементах форм (`input`, `select`, `textarea`) директива `v-model` связывает значение элемента с реактивной переменной: ввод пользователя обновляет данные, обновление данных — поле.

На **компонентах** `v-model` — это синтаксический сахар над парой «prop вниз + событие вверх»:

```vue
<TaskFilter v-model="filter" />

<!-- эквивалентно -->
<TaskFilter :model-value="filter" @update:model-value="filter = $event" />
```

То есть компонент-ребёнок принимает prop `modelValue` и эмитит событие `update:modelValue` с новым значением. Внутри ребёнка удобно использовать макрос `defineModel` (стабилен с Vue 3.4):

```vue
<!-- TaskFilter.vue -->
<script setup lang="ts">
const filter = defineModel<string>({ required: true })
</script>

<template>
  <select v-model="filter">
    <option value="все">Все</option>
    <option value="активные">Активные</option>
    <option value="готово">Готово</option>
  </select>
</template>
```

Поддерживаются **несколько моделей** на одном компоненте — например, форма создания задачи:

```vue
<!-- TaskForm.vue -->
<script setup lang="ts">
const title = defineModel<string>('title', { required: true })
const description = defineModel<string>('description', { default: '' })
</script>

<template>
  <form @submit.prevent>
    <input v-model="title" placeholder="Название задачи" />
    <textarea v-model="description" placeholder="Описание" />
  </form>
</template>
```

```vue
<!-- использование в родителе -->
<TaskForm v-model:title="draft.title" v-model:description="draft.description" />
```

Модификаторы (`v-model.trim`, `v-model.number`, а также пользовательские, например `v-model.capitalize`) позволяют трансформировать значение «по пути».

> 💡 `v-model` на компоненте не магия и не «нарушение однонаправленного потока». Это просто короткая запись: данные всё так же спускаются через prop, а наверх поднимается событие. Меняется только количество клавиш, которые вы успеваете стереть.

### 8.7. Хуки жизненного цикла компонента

Каждый компонент проходит стадии: **создание** (setup) → **монтирование** в DOM (mount) → **обновления** (updates) → **размонтирование** (unmount). Хуки жизненного цикла (lifecycle hooks) позволяют выполнить код в нужный момент.

| Хук (Composition API) | Стадия | Типичное применение |
|---|---|---|
| (сам код `setup`) | создание | инициализация состояния, computed, подписки без DOM |
| `onBeforeMount` | перед монтированием | редко; DOM ещё не существует |
| `onMounted` | после монтирования | работа с DOM, запросы данных, сторонние библиотеки виджетов |
| `onBeforeUpdate` | перед перерисовкой | редко; чтение «старого» DOM |
| `onUpdated` | после перерисовки | осторожно: следите, чтобы не зациклить обновления |
| `onBeforeUnmount` | перед удалением | последние приготовления к очистке |
| `onUnmounted` | после удаления | **обязательная** очистка: слушатели, таймеры, соединения |
| `onErrorCaptured` | ошибка у потомка | локальная обработка ошибок |

```ts
import { onMounted, onUnmounted } from 'vue'

onMounted(() => {
  // DOM уже существует: можно измерять, фокусировать, подключать библиотеки
  inputEl.value?.focus()
})

onUnmounted(() => {
  // компонент удалён: убираем за собой, иначе — утечка памяти
  window.removeEventListener('keydown', onKeyDown)
})
```

Важные детали:

- в Composition API нет хука «onCreated» — его роль выполняет сам код `setup`, выполняющийся при создании;
- хуки регистрируются **синхронно во время setup** — их нельзя вызывать из отложенных колбэков (например, из `setTimeout`);
- всё, что вы подключили в `onMounted` (слушатели событий, `setInterval`, WebSocket), должно быть отключено в `onUnmounted`. Компонент в SPA может монтироваться и размонтироваться десятки раз за сессию;
- порядок хуков в дереве: `onBeforeMount` родителя вызывается раньше дочерних, а `onMounted` дочерних — раньше родительского. Дерево «собирается» сверху вниз, но сообщения о готовности приходят снизу вверх.

> ⚠️ Частая ошибка: обращаться к DOM в `setup` или `onBeforeMount` — элемента там ещё физически нет, `ref` на шаблон вернёт `undefined`. DOM доступен начиная с `onMounted`.

## Домашнее задание

**Реализовать компонент модального окна с управлением через `v-model` и телепортацией в `body`.**

Состав:

1. Компонент `ModalWindow.vue`:
   - открывается/закрывается через `v-model` (используйте `defineModel<boolean>`);
   - контент передаётся через слот (slot), заголовок — через prop или именованный слот;
   - рендерится в `body` через встроенный компонент `<Teleport to="body">`;
   - закрывается по `Escape` и по клику на подложку (overlay);
   - имеет базовую стилизацию и `aria-modal="true"`.
2. Интеграция в проект: кнопка «Удалить» в `TaskItem` сначала открывает модалку подтверждения «Удалить задачу?», фактическое удаление происходит только после подтверждения.

### Требования к сдаче

- проект запускается `npm run dev` без ошибок TypeScript в strict-режиме;
- компонент переиспользуемый: в нём нет никакой бизнес-логики приложения, только «окно»;
- в репозитории коммиты по Conventional Commits (например, `feat: add ModalWindow component`).

### Критерии оценки

1. Корректная работа `v-model`: модалка управляется из родителя одной переменной (до 3 баллов).
2. `Teleport` в `body`, слоты, закрытие по Escape/подложке (до 3 баллов).
3. Типизация props/emits/models, strict-режим без ошибок (до 2 баллов).
4. Доступность и аккуратность стилей (до 1 балла).
5. Сверх ожиданий: блокировка скролла фона и возврат фокуса на кнопку-инициатор (до 1 балла).

## Типичные ошибки и заблуждения

1. **«Я изменил данные, а экран не обновился»** — почти всегда это деструктуризация реактивного объекта или забытый `.value` у `ref` вне шаблона.
2. **Мутация props в ребёнке.** Prop — только для чтения; локальные изменения делайте через копию или событие родителю.
3. **Замена `reactive`-объекта целиком** (`state = reactive({...})`): переменная указывает на новый объект, старый прокси и его подписчики «брошены». Нужно `Object.assign(state, {...})` либо использовать `ref`.
4. **Обращение к DOM в `setup`** вместо `onMounted` — элемент ещё не существует.
5. **Подписался и не отписался**: слушатели и таймеры без `onUnmounted` превращаются в утечки памяти (подробнее — в теме 10).
