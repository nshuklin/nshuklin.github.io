# Тема 4. TypeScript в кроссплатформенном проекте

## Аннотация

TypeScript давно перестал быть «опциональной надстройкой для энтузиастов»: сегодня это стандарт индустрии для любых проектов серьёзнее прототипа, а Vue 3 и вовсе написан на нём. В этой теме мы освоим строгую типизацию: базовые типы и разницу между `interface` и `type`, дженерики (generics), встроенные utility-типы, сужение типов (narrowing) и строгий режим компилятора.

## Цель темы

**Цель:** научиться использовать строгую типизацию для надёжности кода.

После изучения темы вы будете знать/уметь:

1. **знать** базовые типы TypeScript и отличия `interface` от `type` с критериями выбора;
2. **знать** стандартные utility-типы (`Partial`, `Pick`, `Omit`, `Record` и др.) и типовые сценарии их применения;
3. **уметь** писать обобщённый код на дженериках, включая ограничения (`extends`) и значения по умолчанию;
4. **уметь** применять narrowing и type guards, включая дискриминированные объединения (discriminated unions);
5. **уметь** настраивать `tsconfig.json` в строгом режиме (strict mode) и читать сообщения компилятора без паники.

## Теоретическая часть

### 4.1. Зачем нужен TypeScript и как он устроен

TypeScript (TS) — язык программирования, разработанный Microsoft: это **надмножество JavaScript** со статической типизацией. Любой корректный JS-код является корректным TS-кодом; TypeScript лишь добавляет систему типов, которая проверяет код **на этапе компиляции** и бесследно исчезает из результата: компилятор `tsc` стирает типы и выдаёт обычный JavaScript.

Что это даёт на практике:

1. **Ошибки до запуска, а не в проде.** Опечатку в имени поля, `undefined` вместо объекта, неверный аргумент функции компилятор подсветит ещё в редакторе. Классическое «Cannot read properties of undefined (reading 'length')» в TS-проектах чаще всего не проходит дальше IDE.
2. **Документация, которая не врёт.** Сигнатура `moveTask(tasks: Task[], id: string, status: TaskStatus): Task[]` рассказывает о функции больше, чем любой комментарий (и, в отличие от комментария, не устаревает).
3. **Автодополнение и рефакторинг.** Редактор знает структуру данных и предлагает поля, переименования и импорты сам.
4. **Безопасность рефакторинга.** Поменяли поле в интерфейсе — компилятор покажет все места, которые нужно починить. Ничего не потеряется.

> 💡 Полезно знать: TypeScript проверяет только то, что вы ему рассказали. Типы не существуют во время выполнения (runtime): проверить, что в функцию пришёл именно объект задачи из сети, компилятор не может — для runtime-валидации используют zod, valibot или ручные проверки. TS защищает от ошибок программиста, а не от лживого сервера.

Минимальный цикл работы:

```bash
npm install -D typescript   # компилятор tsc
npx tsc app.ts              # компиляция в app.js
node app.js                 # запуск результата
```

В боевых проектах компиляцию обычно выполняет сборщик (Vite, о котором мы поговорим в теме 6), а `tsc` остаётся для проверки типов.

### 4.2. Базовые типы

Начнём с повседневного набора. Аннотация типа записывается после имени: `const x: number = 42`.

```ts
// Примитивы
const title: string = 'Деплой';
const isDone: boolean = false;
const taskId: number = 42;
const nothing: null = null;
const notYet: undefined = undefined;

// Массивы — две равнозначные записи
const tags: string[] = ['релиз', 'баг'];
const scores: Array<number> = [1, 2, 3];

// Кортеж (tuple): фиксированная длина и типы по позициям
const kanbanColumn: [string, number] = ['В работе', 3];

// Объединение (union): «или-или»
const deadline: string | null = '2026-09-01';

// Литеральный тип: только конкретные значения
type TaskStatus = 'К выполнению' | 'В работе' | 'Готово';
const status: TaskStatus = 'В работе';
// status = 'Сделано'; // 💥 ошибка компиляции: такого статуса нет
```

Литеральные объединения — рабочая лошадка. Например, когда так мы описываем статусы, тогда опечатка в статусе станет ошибкой компиляции, а не багом в продакшене. 

Особые типы, которые нужно различать:

| Тип | Что означает | Когда использовать |
| --- | --- | --- |
| `any` | «отстань от меня, компилятор»; проверка типов отключается | Почти никогда; в миграциях legacy — временно |
| `unknown` | значение неизвестного типа; использовать можно только после проверки | Результаты `fetch`, парсинг JSON, границы системы |
| `never` | «никогда»: функция не возвращается, недостижимая ветка | Обработка ошибок, проверка исчерпывающих `switch` |
| `void` | функция ничего не возвращает | Колбэки, обработчики событий |

Правило курса: **`any` запрещён** (в учебном коде — с редчайшими исключениями). Не знаете тип — берите `unknown` и проверяйте.

### 4.3. Интерфейсы и типы: interface против type

Структуру объектов описывают двумя способами:

```ts
// interface
interface Task {
  id: string;
  title: string;
  status: TaskStatus;
  tags: string[];
  deadline: string | null;
}

// type
type TaskAsType = {
  id: string;
  title: string;
  status: TaskStatus;
  tags: string[];
  deadline: string | null;
};
```

Для простых объектов они взаимозаменяемы, но есть принципиальные отличия:

| Критерий | `interface` | `type` |
| --- | --- | --- |
| Объединения/пересечения (`A \| B`, `A & B`) | Нет | Да |
| Алиасы примитивов и кортежей | Нет | Да |
| Наследование | `extends` | Пересечение `&` |
| Дополнение объявления (declaration merging) | Да: два `interface` с одним именем объединяются | Нет: повторное имя — ошибка |
| Сообщение об ошибках | Обычно «форма объекта» | Иногда удобнее для сложных типов |

```ts
// Наследование
interface DeadlineTask extends Task {
  remindBefore: number; // за сколько часов напомнить
}

// Объединения доступны только через type
type LoadState = 'idle' | 'loading' | 'done';
type TaskOrError = Task | ApiError;
```

Практическое правило выбора:

- **`interface`** — для форм объектов, особенно публичных контрактов (модели предметной области, props компонентов): читается как «объект обязан иметь такую форму» и поддерживает расширение;
- **`type`** — для объединений, литералов, кортежей, служебных композиций.

Оба подхода используют generics, оба компилируются «в ноль». Спор о превосходстве одного над другим длится десятилетие.

### 4.4. Дженерики (Generics)

Дженерики — это **параметры типов**: способ писать код, который работает с любым типом, не теряя типизацию. Метафора: дженерик — универсальная коробка-трансформер. Вы пишете инструкцию для коробки вообще, а при использовании сообщаете, какой груз внутрь положить — и коробка «перестраивается» под него.

```ts
// Без дженериков пришлось бы писать для каждого типа...
function firstTask(arr: Task[]): Task { return arr[0]; }
function firstString(arr: string[]): string { return arr[0]; }

// ...а с дженериками — одна функция на все случаи
function first<T>(arr: T[]): T | undefined {
  return arr[0];
}

first(tasks);   // T выведен как Task, результат — Task | undefined
first(['a']);   // T выведен как string
```

Чаще всего компилятор **выводит** параметр сам из аргументов — указывать `<Task>` явно приходится редко.

Дженерики работают и в типах. Классический пример — ответ API, «упакованный» в общий конверт:

```ts
interface ApiResponse<T> {
  data: T;
  status: number;
  timestamp: string;
}

type ProjectsResponse = ApiResponse<Project[]>; // конверт с проектами
type TaskResponse = ApiResponse<Task>;          // конверт с задачей
```

Два важных расширения механизма:

**Ограничения** (`extends`) — требование к типу:

```ts
interface HasId {
  id: string;
}

// принимает только массивы объектов с полем id
function findById<T extends HasId>(items: T[], id: string): T | undefined {
  return items.find((item) => item.id === id);
}
```

**Значения по умолчанию** — если параметр не указали:

```ts
interface Paginated<T = Task> {
  items: T[];
  page: number;
  total: number;
}

const page: Paginated = { items: tasks, page: 1, total: 42 }; // T = Task
```

### 4.5. Utility Types: стандартные «трансформеры» типов

В TypeScript встроена коллекция utility-типов — готовых преобразователей, которые избавляют от дублирования описаний. Самые используемые:

| Utility-тип | Что делает | Пример |
| --- | --- | --- |
| `Partial<T>` | Все свойства необязательные | Обновление задачи: `updateTask(id, Partial<Task>)` |
| `Required<T>` | Все свойства обязательные | Обратное превращение |
| `Readonly<T>` | Все свойства только для чтения | Иммутабельность на уровне типов |
| `Pick<T, K>` | Выбрать перечисленные поля | `Pick<Task, 'id' \| 'title'>` |
| `Omit<T, K>` | Исключить перечисленные поля | `Omit<Task, 'id'>` — данные новой задачи |
| `Record<K, V>` | Объект с ключами `K` и значениями `V` | `Record<TaskStatus, Task[]>` — группировка |
| `ReturnType<F>` | Тип возвращаемого значения функции | Для вывода сложных типов |
| `NonNullable<T>` | Убрать `null` и `undefined` | Работа с опциональными полями |

Типичные сценарии в TaskFlow:

```ts
// Создание задачи: id присваивает сервер, клиент его не отправляет
type NewTask = Omit<Task, 'id'>;

// Редактирование: присылают только изменённые поля
type TaskPatch = Partial<Omit<Task, 'id'>>;

// Группировка задач по статусам канбан-доски
type KanbanBoard = Record<TaskStatus, Task[]>;

// Только публичные поля для отображения в списке
type TaskListItem = Pick<Task, 'id' | 'title' | 'status'>;

// Иммутабельность (привет из темы 2!)
const frozenTask: Readonly<Task> = task;
// frozenTask.status = 'Готово'; // 💥 ошибка компиляции
```

> 💡 Полезно знать: `Record<TaskStatus, Task[]>` заставляет описать **все** статусы — компилятор не позволит забыть колонку доски. Такие «исчерпывающие» типы — дешёвый способ ловить логические ошибки.

### 4.6. Narrowing и Type Guards

Часто значение имеет несколько возможных типов (union), и код должен работать по-разному для каждого случая. **Сужение типа** (narrowing) — процесс, при котором компилятор по проверкам в коде понимает, какой именно тип перед ним.

Основные приёмы:

```ts
function describe(deadline: string | null): string {
  if (deadline === null) {
    return 'Без дедлайна';
  }
  // здесь компилятор уже знает: deadline — string
  return `Дедлайн: ${deadline}`;
}

function format(value: string | number): string {
  if (typeof value === 'string') {
    return value.toUpperCase(); // здесь value: string
  }
  return value.toFixed(2); // здесь value: number
}
```

Виды проверок (type guards), которые понимает компилятор:

1. **`typeof`** — для примитивов (`'string'`, `'number'`, `'boolean'`).
2. **Проверки на `null`/`undefined`** и truthiness (`if (value)`).
3. **Оператор `in`** — наличие свойства: `if ('deadline' in item)`.
4. **`instanceof`** — для классов.
5. **Пользовательские предикаты** — функция, возвращающая `x is T`:

```ts
function isTask(value: unknown): value is Task {
  return (
    typeof value === 'object' &&
    value !== null &&
    'id' in value &&
    'title' in value &&
    'status' in value
  );
}

const parsed: unknown = JSON.parse(responseText);
if (isTask(parsed)) {
  console.log(parsed.title); // компилятор поверил предикату
}
```

6. **Дискриминированные объединения** (discriminated unions) — самый мощный приём: у всех вариантов объединения есть общее поле-«метка» (discriminant), по которому `switch` разбирает случаи:

```ts
type NotificationEvent =
  | { kind: 'task-created'; taskId: string }
  | { kind: 'task-moved'; taskId: string; newStatus: TaskStatus }
  | { kind: 'comment-added'; taskId: string; author: string };

function describeEvent(event: NotificationEvent): string {
  switch (event.kind) {
    case 'task-created':
      return `Создана задача ${event.taskId}`;
    case 'task-moved':
      return `Задача ${event.taskId} → ${event.newStatus}`;
    case 'comment-added':
      return `${event.author} оставил комментарий к ${event.taskId}`;
  }
}
```

Если в `NotificationEvent` добавится четвёртый вариант, компилятор подсветит, что `switch` стал не исчерпывающим (а с проверкой на `never` в `default` — укажет явно).

> ⚠️ Частая ошибка: пытаться проверить тип во время выполнения через `typeof` для интерфейсов: `typeof value === 'Task'` бессмысленно — типов на этапе выполнения не существует. Runtime-проверки работают только через реальные данные: поля объекта, `instanceof`, предикаты.

### 4.7. Strict mode: строгий режим компилятора

Флаг `"strict": true` в `tsconfig.json` включает набор проверок, превращающих TypeScript из «доброго помощника» в строгого контролёра на входе в проект. Что входит в строгий режим:

| Флаг | Что проверяет |
| --- | --- |
| `noImplicitAny` | Запрещает неявный `any`: у всего должны быть типы (хотя бы выведенные) |
| `strictNullChecks` | `null` и `undefined` — полноценные типы; нельзя сунуть их куда попало |
| `strictFunctionTypes` | Корректная проверка типов аргументов функций |
| `strictBindCallApply` | Проверка аргументов `call`/`apply`/`bind` |
| `strictPropertyInitialization` | Поля класса должны быть инициализированы в конструкторе |
| `noImplicitThis` | Запрещает «потерянный» `this` без типа |
| `useUnknownInCatchVariables` | В `catch (error)` переменная имеет тип `unknown`, а не `any` |

Практическое следствие `strictNullChecks`: поле `deadline: string | null` **обязывает** проверить на `null` перед использованием. Это звучит как бюрократия, но именно этот флаг ловит львиную долю runtime-падений ещё до запуска программы.

Дополнительные флаги, которые стоит включить в учебном проекте (не входят в `strict`, но полезны):

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "Bundler",
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "noUnusedLocals": true,
    "noUnusedParameters": true,
    "noFallthroughCasesInSwitch": true,
    "skipLibCheck": true
  },
  "include": ["src"]
}
```

Разбор «экзотических» флагов:

- `noUncheckedIndexedAccess` — обращение по индексу (`arr[i]`) получает тип `T | undefined`, потому что элемента может не существовать. Больно первые два дня, потом не можете без него жить.
- `noUnusedLocals` / `noUnusedParameters` — мёртвый код не пройдёт компиляцию.
- `noFallthroughCasesInSwitch` — забывчивый `break` в `switch` становится ошибкой.

## Типичные ошибки и заблуждения

1. **`any` как спасательный круг.** Каждый `any` — это дыра, через которую ошибки пробираются обратно в runtime. Не знаете тип — используйте `unknown` и сужайте проверками.
2. **«Убедительное» приведение типов через `as`.** `const task = data as Task` не делает данные задачей — это обещание компилятору, за которое отвечаете вы. Сетевые данные сначала проверяйте (предикат, zod), потом приводите.
3. **Пренебрежение `strictNullChecks`.** Без него `deadline.length` на `null` компилируется и падает в продакшене. Строгий режим включается в первый день, а не «когда будет время».
4. **Проверка интерфейсов через `typeof`.** Типы стираются при компиляции: `typeof x === 'Task'` не работает и не заработает. Runtime-проверки строятся на данных: поля, `instanceof`, предикаты `x is T`.
5. **Дженерики «на всякий случай».** Параметр типа, который используется один раз и не связывает части сигнатуры, только усложняет чтение. Дженерик нужен, когда тип **повторяется** или **преобразуется** (вход связан с выходом, коллекция связана с элементом).
