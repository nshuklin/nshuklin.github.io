# Тема 7. Инфраструктура проекта: Git, npm/pnpm, Vite, ESLint, Prettier

## Аннотация

Командный проект — это не только код, но и инфраструктура вокруг него: система контроля версий, пакетный менеджер, сборщик, линтер, форматтер и гит-хуки, которые не дают хаосу пройти в репозиторий. В этой теме мы настроим «хозяйственный пояс» учебного проекта: научимся вести историю по Conventional Commits, управлять зависимостями через pnpm, собирать проект Vite и защищать репозиторий связкой ESLint + Prettier + Husky + lint-staged. Бонусом поймём, почему каждый инструмент решает свою задачу и почему менять их местами — плохая примета.

## Цель темы

**Цель:** настроить современный и жёсткий инструментарий для командной разработки.

После изучения темы вы будете знать/уметь:

- **знать** модель ветвления Git Flow и спецификацию Conventional Commits;
- **знать** отличия pnpm от npm и устройство монорепозиториев с воркспейсами (workspaces);
- **понимать**, как Vite работает в режиме разработки и чем сборка отличается от dev-сервера;
- **уметь** настраивать ESLint (flat config) и Prettier так, чтобы они не конфликтовали;
- **уметь** настраивать pre-commit и commit-msg хуки с помощью Husky и lint-staged.

## Теоретическая часть

### 7.1. Контроль версий: Git Flow и Conventional Commits

Система контроля версий Git хранит не файлы, а историю их изменений. Качество этой истории определяет, насколько приятно работать в команде: можно ли найти виновника регрессии за минуту или придётся устраивать археологические раскопки.

**Модель ветвления Git Flow** (предложена Винсентом Дриссеном в 2010 году) описывает роли веток в проекте с регулярными релизами:

| Ветка | Назначение | Жизненный цикл |
| --- | --- | --- |
| `main` | Всегда готовый к релизу код; каждый коммит — потенциальная версия | Вечная |
| `develop` | Интеграция текущей разработки | Вечная |
| `feature/<имя>` | Одна новая функциональность | От `develop`, обратно в `develop` |
| `release/<версия>` | Подготовка релиза: багфиксы, версии, документация | Из `develop` в `main` и обратно |
| `hotfix/<имя>` | Срочное исправление продакшена | Из `main` в `main` и `develop` |

> 💡 Полезно знать: современный веб часто живёт по упрощённым схемам — trunk-based development или GitHub Flow (одна основная ветка + короткие feature-ветки + pull request). Git Flow остаётся эталонной моделью, которую удобно «упрощать осознанно». В учебном проекте мы используем практичный минимум: `main`, `develop` и `feature/*`.

Имена веток — тоже код. `feature/task-deadline` говорит о содержимом больше, чем `new-branch-2` или `fix-final-final`.

**Conventional Commits** — спецификация формата сообщений коммитов, делающая историю машиночитаемой:

```text
<тип>(<область>): <описание>

[необязательное тело]

[необязательная сноска: BREAKING CHANGE, ссылки на задачи]
```

Основные типы:

| Тип | Когда используется |
| --- | --- |
| `feat` | Новая функциональность |
| `fix` | Исправление ошибки |
| `docs` | Только документация |
| `style` | Форматирование, точки с запятой — без изменения логики |
| `refactor` | Перестройка кода без изменения поведения |
| `perf` | Оптимизация производительности |
| `test` | Тесты |
| `build` | Сборка и зависимости (npm, Vite) |
| `ci` | Конфигурация CI (GitHub Actions) |
| `chore` | Рутина, не попадающая в другие типы |
| `revert` | Откат коммита |

Примеры из жизни учебного проекта:

```text
feat(tasks): добавлен дедлайн в карточку задачи
fix(board): перетаскивание задачи между колонками больше не теряет теги
docs(readme): описан запуск проекта
feat(auth)!: токены переехали из localStorage в IndexedDB
```

Восклицательный знак (или сноска `BREAKING CHANGE:`) отмечает несовместимое изменение. Зачем такая дисциплина? Три причины:

1. **Автоматическое версионирование.** Инструменты семантического версионрования читают типы: `feat` поднимает minor-версию, `fix` — patch, `!` — major.
2. **Автогенерация changelog** — история изменений собирается из коммитов без ручного труда.
3. **Проверяемость.** Линтер коммитов (commitlint) просто не пропустит сообщение «поправил».

> ⚠️ Частая ошибка: думать, что тип `style` — про CSS. Нет, `style` — про форматирование кода. Изменение стилей интерфейса — это `feat` или `fix` с областью `(ui)`.

### 7.2. Пакетные менеджеры: npm против pnpm, монорепо и воркспейсы

Каждый пакет JavaScript тянет за собой зависимости, те — свои, и без пакетного менеджера установка превратилась бы в ручную перепись интернета. Стандартный контракт: `package.json` описывает, что нужно проекту, lock-файл (`package-lock.json`, `pnpm-lock.yaml`) фиксирует точные версии для воспроизводимости, каталог `node_modules` хранит установленное.

**Как работает npm.** Пакеты устанавливаются «плоско» в корневой `node_modules` (hoisting — подъём). Это порождает две хронические болезни:

1. **Фантомные зависимости (phantom dependencies).** Можно импортировать пакет, которого нет в вашем `package.json`, — он «проехал зайцем» вместе с чужой зависимостью. Локально работает, после чистой установки — падает.
2. **Дублирование и конфликты версий.** Десять пакетов с одной зависимостью разных версий раздувают `node_modules` до размеров небольшой операционной системы.

**Как работает pnpm.** Одна копия каждого пакета хранится в глобальном хранилище (store), в проект она подключается жёсткими ссылками (hard links), а внутри `node_modules` строится строгая структура из символических ссылок. Следствия:

| Критерий | npm | pnpm |
| --- | --- | --- |
| Хранение пакетов | Копия в каждом проекте | Одна копия в store + жёсткие ссылки |
| Скорость установки | Базовая | Заметно выше (кэш ссылок) |
| Доступ к пакетам | Всё видно всем (hoisting) | Только заявленное в `package.json` |
| Фантомные зависимости | Возможны | Практически исключены |
| Монорепо | Workspaces (базово) | Workspaces «из коробки», фильтр `--filter` |

> 💡 Полезно знать: строгость pnpm — это перенос боли из будущего в настоящее. Фантомная зависимость, которую npm терпел месяцами, в pnpm ломает сборку в первый же день. Это хорошо: ломается она там, где её чинить дёшево.

**Монорепозиторий (monorepo)** — один репозиторий с несколькими пакетами. Для учебного проекта это естественная форма жизни:

```text
my-app/
├── apps/
│   ├── web/        # веб-приложение (Vue 3)
│   └── mobile/     # конфигурации Capacitor (тема 17)
├── packages/
│   ├── shared/     # типы и утилиты: среды исполнения, storage
│   └── ui/         # переиспользуемые компоненты
├── pnpm-workspace.yaml
└── package.json
```

Воркспейсы объявляются в `pnpm-workspace.yaml`:

```yaml
packages:
  - 'apps/*'
  - 'packages/*'
```

Полезные команды pnpm в монорепо:

```bash
pnpm install                    # установка во всех воркспейсах
pnpm --filter web dev           # запуск dev-сервера в apps/web
pnpm --filter shared build      # сборка пакета shared
pnpm -r lint                    # команда lint во всех пакетах
pnpm add vue --filter web       # зависимость конкретному пакету
```

### 7.3. Vite: dev-сервер и сборщик

Vite (фр. «быстрый») решил главную боль сборщиков прошлого поколения: холодный старт. Webpack перед запуском dev-сервера собирал всё приложение; Vite сказал «а можно не всё?» — и оказался прав.

**Режим разработки (dev).** Ключевая идея: приложение в dev-режиме не собирается вовсе.

1. **Pre-bundling зависимостей.** Сторонние пакеты из `node_modules` один раз прогоняются через esbuild: CommonJS переводится в ES-модули, тысячи мелких файлов склеиваются. Браузеру остаётся загрузить несколько крупных модулей вместо тысяч мелких.
2. **Нативные ES-модули.** Собственный код проекта браузер запрашивает по мере надобности: Vite-сервер превращает `App.vue` и TypeScript в JS прямо в момент запроса.
3. **HMR (Hot Module Replacement).** При изменении файла сервер обновляет только затронутый модуль, не перезагружая страницу. Время обновления не зависит от размера проекта — в отличие от классических сборщиков.

**Режим сборки (build).** Для продакшена dev-подход не годится (сотни запросов по сети, несжатый код), поэтому сборка идёт через Rollup:

| Аспект | Dev-режим | Production-сборка |
| --- | --- | --- |
| Инструмент | Vite-сервер + esbuild (pre-bundle) | Rollup |
| Стратегия | Модули по запросу, без бандла приложения | Оптимизированные бандлы |
| Tree shaking | Минимальный | Полный: неиспользуемый код вырезается |
| Результат | Мгновенный старт и HMR | `dist/`: минификация, хэши, code splitting |

**Плагины** расширяют Vite на обоих этапах. Плагин — объект с хуками (`config`, `resolveId`, `transform`, `handleHotUpdate` и другие). Например, `@vitejs/plugin-vue` превращает `.vue`-файлы в JS на этапе `transform`.

Конфигурация, с которой проект будет жить дальше по курсу:

```ts
// vite.config.ts
import { fileURLToPath, URL } from 'node:url';

import vue from '@vitejs/plugin-vue';
import { defineConfig } from 'vite';

export default defineConfig({
  plugins: [vue()],
  resolve: {
    alias: {
      // Импорт '@/components/TaskCard.vue' вместо '../../components/...'
      '@': fileURLToPath(new URL('./src', import.meta.url)),
    },
  },
  server: {
    port: 5173,
    proxy: {
      // Запросы на /api dev-сервер перешлёт бэкенду — без CORS-боли
      '/api': { target: 'http://localhost:3000', changeOrigin: true },
    },
  },
});
```

> ⚠️ Частая ошибка: объявить алиас `@` только в `vite.config.ts`. Vite будет доволен, а TypeScript — нет: компилятору нужна своя подсказка в `tsconfig` (`baseUrl` + `paths`). Алиасы всегда объявляются в двух местах.

Переменные окружения Vite доступны через `import.meta.env` (`import.meta.env.DEV`, `import.meta.env.PROD`, пользовательские — с префиксом `VITE_`).

### 7.4. Статический анализ: ESLint (flat config) и Prettier

**ESLint** — статический анализатор: он разбирает код в абстрактное синтаксическое дерево (AST) и проверяет правила — от потенциальных ошибок (`no-unused-vars`) до договорённостей команды. Начиная с ESLint 9 единственным форматом конфигурации является **flat config**: файл `eslint.config.js` экспортирует массив объектов конфигурации (старые `.eslintrc.*` отправлены в музей).

```js
// eslint.config.js
import js from '@eslint/js';
import pluginVue from 'eslint-plugin-vue';
import tseslint from 'typescript-eslint';

export default tseslint.config(
  { ignores: ['dist/**', 'coverage/**'] },
  js.configs.recommended,
  ...tseslint.configs.recommended,
  ...pluginVue.configs['flat/recommended'],
  {
    files: ['**/*.vue'],
    languageOptions: {
      parserOptions: { parser: tseslint.parser },
    },
  },
  {
    rules: {
      '@typescript-eslint/no-unused-vars': ['error', { argsIgnorePattern: '^_' }],
      '@typescript-eslint/no-explicit-any': 'error',
    },
  },
);
```

**Prettier** — бескомпромиссный форматтер: он не ищет ошибки, а переписывает код в единый стиль (отступы, кавычки, переносы). Слово «бескомпромиссный» здесь ключевое: споры о стиле в команде заканчиваются в момент установки Prettier, потому что спорить становится не о чем.

```json
// .prettierrc.json
{
  "semi": true,
  "singleQuote": true,
  "printWidth": 100,
  "trailingComma": "all"
}
```

Разделение ответственности:

| Задача | Инструмент |
| --- | --- |
| Потенциальные ошибки, `any`, неиспользуемые переменные | ESLint |
| Отступы, кавычки, переносы строк | Prettier |
| Сообщения коммитов | commitlint (следующий раздел) |

Чтобы инструменты не воевали, пакет `eslint-config-prettier` отключает в ESLint правила форматирования. Современные рекомендации — именно такая связка: Prettier запускается отдельно, а не как правило ESLint.

```jsonc
// package.json
{
  "scripts": {
    "dev": "vite",
    "build": "vue-tsc -b && vite build",
    "lint": "eslint . --fix",
    "format": "prettier --write ."
  }
}
```

### 7.5. Гит-хуки: Husky и lint-staged

Линтер, который запускается «когда-нибудь», не работает никогда. Решение — гит-хуки (Git hooks): скрипты, которые Git выполняет на событиях репозитория (`pre-commit`, `commit-msg`, `pre-push`...).

**Husky** подключает хуки к репозиторию (команда `husky init` выставляет `core.hooksPath` на каталог `.husky`) и делает их частью кодовой базы — хуки попадают в коммиты вместе с кодом.

**lint-staged** отвечает на вопрос «что именно проверять?» — только файлы, добавленные в коммит (staged). Полная проверка проекта в хуке превращает каждый коммит в обеденный перерыв; точечная — занимает секунды.

```jsonc
// package.json
{
  "lint-staged": {
    "*.{ts,vue}": ["eslint --fix", "prettier --write"],
    "*.{css,json,md}": ["prettier --write"]
  }
}
```

```bash
# .husky/pre-commit
pnpm exec lint-staged
```

```bash
# .husky/commit-msg
npx --no -- commitlint --edit $1
```

```js
// commitlint.config.js
export default { extends: ['@commitlint/config-conventional'] };
```

Итог: коммит с сообщением «поправил» будет отклонён commitlint; коммит с неиспользуемой переменной — отклонён ESLint; в репозиторий попадает только то, что прошло контроль.

> ⚠️ Частая ошибка: запускать в pre-commit проверку всего проекта (`pnpm lint` без lint-staged). Хук начинает занимать минуты, и команда знакомится с флагом `--no-verify` — аварийным выходом, который быстро становится главным входом.

> 💡 Полезно знать: обойти хуки можно (`git commit --no-verify`), как можно обойти турникет в метро. Инструмент оставляет такую возможность для форс-мажоров; команда — договорённость этой возможностью не злоупотреблять.

## Домашнее задание

**Настроить CI-проверку (GitHub Actions), которая гоняет линтер и тесты при пуше.**

Проект должен проверяться автоматически на каждый `push` в ветки `main`/`develop` и на каждый pull request:

1. Создайте файл `.github/workflows/ci.yml` в репозитории проекта.
2. Настройте шаги: checkout кода, установка pnpm и Node.js (с кэшем pnpm), `pnpm install --frozen-lockfile`, запуск `pnpm lint`.
3. Добавьте скрипт-заглушку для тестов (настоящие тесты появятся в теме 16): `"test": "echo \"Тесты появятся в теме 16\" && exit 0"` — и запускайте его отдельным шагом.
4. Добавьте в `README.md` бейдж статуса workflow.
5. Убедитесь, что проверка «зелёная», и сделайте скриншот вкладки Actions.

Шаблон для старта:

```yaml
name: CI

on:
  push:
    branches: [main, develop]
  pull_request:

jobs:
  lint-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
        with:
          version: 9
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: pnpm
      - run: pnpm install --frozen-lockfile
      - run: pnpm lint
      - run: pnpm test
```

### Требования к сдаче

- Файл `.github/workflows/ci.yml` в репозитории; история коммитов — по Conventional Commits;
- workflow запускается на `push` в `main`/`develop` и на pull request;
- установлены pnpm и Node.js с кэшированием зависимостей, установка идёт с `--frozen-lockfile`;
- бейдж CI в `README.md`;
- скриншот вкладки Actions с успешным (и хотя бы одним проваленным для демонстрации) запуском.

### Критерии оценки

1. Workflow корректно срабатывает на `push` и `pull_request`, все шаги выполняются на актуальном Node.js с кэшем pnpm.
2. Линтер действительно запускается: если в PR намеренно внести ошибку `any`, CI падает — поведение продемонстрировано.
3. Используется `--frozen-lockfile`: CI проверяет ровно тот lock-файл, что в репозитории.
4. Бейдж статуса отображается в `README.md` и отражает реальное состояние ветки.
5. История коммитов домашней работы соответствует Conventional Commits (проверяется по `git log`).

## Типичные ошибки и заблуждения

1. **Коммиты-загадки.** Сообщения «поправил», «fix», «финальная версия 2» делают историю бесполезной. Conventional Commits — не бюрократия, а интерфейс к вашей истории.
2. **Алиас только в Vite.** Без `paths` в `tsconfig` TypeScript не понимает `@/`, и проект живёт в состоянии «запускается, но весь в красных подчёркиваниях».
3. **Война ESLint и Prettier.** Без `eslint-config-prettier` правила форматирования двух инструментов конфликтуют, и каждый запуск `lint --fix` отменяет работу форматтера.
4. **Фантомные зависимости.** Импортировать пакет, которого нет в `package.json`, — локально работает (спасибо hoisting npm), в CI или у коллеги падает. pnpm делает такие сюрпризы невозможными — пользуйтесь этим.
5. **Тяжёлые хуки.** `pnpm lint` по всему проекту в pre-commit превращает коммит в испытание терпения и учит команду флагу `--no-verify`. Только lint-staged, только staged-файлы.
