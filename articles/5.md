# Тема 5. Среды исполнения JavaScript

## Аннотация

JavaScript не живёт сам по себе — он всегда работает внутри среды исполнения (runtime environment). Браузер, Node.js, мобильное WebView: везде один и тот же ECMAScript, но набор доступных API отличается радикально. В этой теме мы детально разберём браузерную среду как главную площадку для кроссплатформенной разработки, а также поймём, чем от неё отличаются серверная и мобильные среды, и как писать код, работающий в любой из них.

## Цель темы

**Цель:** освоить браузерную среду исполнения и понимать её отличия от других сред.

После изучения темы вы будете знать/уметь:

- **знать** устройство браузерной среды: DOM, BOM, Web API и модель безопасности;
- **понимать** ключевые отличия Node.js от браузера и когда какая среда уместна;
- **понимать** принцип работы JS-мостов в мобильных приложениях;
- **уметь** определять среду исполнения во время работы программы;
- **уметь** писать изоморфный код через `typeof`-проверки и `globalThis`.

## Теоретическая часть

### 5.1. Из чего складывается среда исполнения

«Чистый» JavaScript умеет подозрительно мало. Стандарт ECMAScript описывает синтаксис, типы данных, функции, классы и встроенные объекты (`Array`, `Map`, `Set`, `Promise`, `JSON` и компанию) — и почти ничего сверх этого. Ни `console`, ни `setTimeout`, ни `fetch` в стандарте нет: всё это добавляет среда исполнения.

Запомним формулу:

> **JavaScript-программа = движок ECMAScript + API среды исполнения.**

Движок JavaScript читает и выполняет код. Основные движки:

| Движок | Где используется |
| --- | --- |
| V8 | Chrome, Edge, Node.js, Electron, системный WebView в Android |
| SpiderMonkey | Firefox |
| JavaScriptCore | Safari, WebKit, WebView в iOS |

Аналогия: ECMAScript — партитура, движок — оркестр, а среда исполнения — концертный зал со своим набором инструментов. В зале «Браузер» есть орган под названием DOM, в зале «Node.js» — файловая система. Партитура одна, звучит по-разному.

Из этого следуют два вывода:

1. Код, не трогающий средо-специфичные API, работает в нескольких средах без изменений.
2. Ошибка `ReferenceError: document is not defined` — это не ошибка языка. Это код попытался сыграть партию органа в зале, где органа нет.

### 5.2. Браузер: окно, документ и Web API

Браузерная среда предоставляет программе три больших блока API:

1. **DOM (Document Object Model)** — объектная модель документа: дерево элементов страницы, доступное через `document`. Позволяет читать и менять разметку, реагировать на события.
2. **BOM (Browser Object Model)** — модель браузера, всё, что не относится к странице: `location` (адрес), `navigator` (данные о браузере и системе), `history` (навигация), `screen` (параметры экрана).
3. **Web API** — прикладные возможности: `fetch`, таймеры, `localStorage`, `WebSocket`, `Geolocation`, `Notifications`, `Canvas` и десятки других.

Глобальный объект среды — `window` (он же `self`). Любой `var`, объявленный на верхнем уровне скрипта, становится свойством `window` — историческая особенность, о которой лучше помнить, чем пользоваться.

```js
// Всё ниже предоставлено браузером, а не языком JavaScript
console.log(document.title);        // DOM: заголовок страницы
console.log(navigator.userAgent);   // BOM: строка о браузере и ОС
fetch('/api/data');                 // Web API: сетевой запрос
setTimeout(() => {}, 1000);         // Web API: таймер
```

Безопасность браузерной среды строится на двух принципах:

- Скрипт выполняется в изолированном процессе рендеринга и практически не имеет прямого доступа к операционной системе.
- Политика одинакового происхождения (same-origin policy) запрещает скрипту читать данные чужого сайта, если тот не разрешил это явно (через CORS).

> 💡 Именно поэтому веб-приложение «из коробки» не может прочитать произвольный файл с диска. Любой доступ к файлам начинается с явного действия пользователя — например, выбора файла через `<input type="file">`.

### 5.3. Node.js: V8 без окна, но с файлами

В 2009 году Райан Даль взял движок V8 из Chrome и добавил к нему библиотеку libuv для событийного цикла и операций ввода-вывода. Так появился Node.js — среда исполнения JavaScript вне браузера.

Страницы в Node.js нет, поэтому DOM и BOM отсутствуют:

```js
console.log(typeof document); // 'undefined'
console.log(typeof window);   // 'undefined'
```

Зато есть то, чего браузеру не положено: модули `node:fs` (файловая система), `node:path` (пути), `node:http` (сервер и клиент), `node:os` (информация об ОС), а также `process` для управления процессом (`process.env`, `process.argv`, `process.exit()`).

Ключевое различие в модели безопасности: браузерный код изолирован песочницей, а Node.js-процесс имеет полный доступ к операционной системе с правами запустившего пользователя.

> ⚠️ В разных средах `setTimeout` возвращает разный тип: в браузере — `number`, в Node.js — объект `Timeout`. В TypeScript для переносимого кода используйте `ReturnType<typeof setTimeout>`.

### 5.4. Сравнение: браузер против Node.js

| Критерий | Браузер | Node.js |
| --- | --- | --- |
| Движок | V8 / SpiderMonkey / JavaScriptCore | V8 |
| Глобальный объект | `window` (`self`) | `global` |
| DOM / BOM | Есть | Нет |
| Типичный ввод-вывод | Сеть (`fetch`), `localStorage` | Файлы (`node:fs`), сокеты |
| Управление процессом | Отсутствует | `process` (env, argv, exit) |
| Модель безопасности | Песочница + same-origin | Полный доступ к ОС |
| Модули | ES-модули | CommonJS (`require`) и ES-модули |

### 5.5. Мобильные платформы: WebView и JS-мосты

В мобильных приложениях JavaScript живёт внутри **WebView** — нативного компонента операционной системы: `WKWebView` в iOS и системный `WebView` в Android. Это тот же браузерный движок (JavaScriptCore или V8), но с дополнительными ограничениями: прямой доступ к камере, геолокации, файловой системе из JavaScript отсутствует — всё это требует нативных плагинов и системных разрешений.

Связь JavaScript с нативным кодом (Kotlin/Java на Android, Swift на iOS) осуществляется через **JS-мост** — механизм асинхронного обмена сериализованными сообщениями. Через мост проходят только данные, сериализуемые в JSON: функции, DOM-элементы и классы передать нельзя.

Низкоуровневые механизмы:

| Платформа | JS → нативная часть | Нативная часть → JS |
| --- | --- | --- |
| Android | `WebView.addJavascriptInterface()` | `WebView.evaluateJavascript()` |
| iOS | `window.webkit.messageHandlers.<имя>.postMessage(...)` | `WKWebView.evaluateJavaScript(...)` |

Высокоуровневые фреймворки (Capacitor) прячут эти детали за API плагинов:

```ts
import { Device } from '@capacitor/device';

const info = await Device.getInfo();
console.log(info.platform); // 'ios' или 'android'
```

> ⚠️ Вызов через мост всегда асинхронный и дороже обычного вызова функции. Группируйте запросы и не гоняйте через мост мегабайты данных.

### 5.6. globalThis и изоморфный код

До ES2020 единого имени для глобального объекта не существовало:

| Объект | Браузер | Node.js | Web Worker |
| --- | --- | --- | --- |
| `window` | ✅ | ❌ | ❌ |
| `self` | ✅ (псевдоним `window`) | ❌ | ✅ |
| `global` | ❌ | ✅ | ❌ |
| `globalThis` | ✅ | ✅ | ✅ |

`globalThis` (ES2020) — единственное имя глобального объекта, работающее везде.

Проверки среды строятся на операторе `typeof` — единственном, который не бросает `ReferenceError` для необъявленных переменных:

```ts
const isBrowser =
  typeof window !== 'undefined' && typeof document !== 'undefined';

const isNode =
  typeof process !== 'undefined' && process.versions?.node != null;
```

> ⚠️ Частая ошибка: писать `if (window)` вместо `typeof window !== 'undefined'`. В Node.js первый вариант завершится `ReferenceError` ещё до вычисления условия.

**Изоморфный код** — код, работающий в нескольких средах. Две тактики:

1. **Определение среды** — спросить «где я?» и выбрать ветку.
2. **Определение возможностей** (feature detection) — спросить «что здесь можно?».

Вторая тактика надёжнее: среда может эмулироваться, а наличие конкретного API — факт.

```ts
export function hasLocalStorage(): boolean {
  try {
    return (
      typeof window !== 'undefined' &&
      typeof window.localStorage !== 'undefined'
    );
  } catch {
    return false;
  }
}
```

Главное правило: платформенный код (обращение к `window`, `document`, `process`) должен быть внутри функций, а не на верхнем уровне модуля. Иначе импорт модуля уронит всё приложение в «не той» среде.

Типовой приём: **единый интерфейс — несколько реализаций**.

```ts
export interface KeyValueStorage {
  getItem(key: string): Promise<string | null>;
  setItem(key: string, value: string): Promise<void>;
}

// Реализация для браузера — localStorage
// Реализация для Node.js — файл
// Фабрика выбирает реализацию по результатам проверки среды
```

Современные сборщики (Vite) умеют заменять константы вроде `import.meta.env.SSR` на этапе сборки и вырезать неиспользуемые ветки из бандла. Изоморфность не обязательно оплачивается размером.

## Типичные ошибки и заблуждения

1. **«Если код работает в браузере, он заработает и в Node.js».** Не заработает: в Node.js нет `document`, `window`, `localStorage` и `navigator`. Переносите только то, что опирается на ECMAScript и общие API (`setTimeout`, `Promise`, `fetch` в новых версиях).
2. **Проверка `if (window)` вместо `typeof window !== 'undefined'`.** Первая конструкция бросает `ReferenceError` в среде без `window` ещё до проверки условия.
3. **Платформенный код на верхнем уровне модуля.** `const root = document.getElementById('app')` вне функции ломает импорт модуля в любой «не той» среде.
4. **`window` внутри Web Worker.** В воркерах глобальный объект — `self`, а `window` и `document` отсутствуют полностью. Используйте `globalThis`.
5. **«В WebView всё доступно как в обычном браузере».** Камера, геолокация и файловая система в мобильном контейнере требуют плагинов и системных разрешений. Без них Web API вежливо (или не очень) откажут.
