# Тема 6. Архитектура кроссплатформенных приложений


## Аннотация

Пока в приложении три компонента, архитектура ему не нужна — достаточно аккуратности. Когда компонентов становится триста, главным вопросом становится не «как написать», а «как разложить» код, чтобы через год в нём можно было ориентироваться без карты и экскаватора. В этой теме разберём архитектуру SPA-приложений, классические паттерны MVC и MVVM, разделение кода на слои (UI, бизнес-логику и слой данных), методологию Feature-Sliced Design и внедрение зависимостей (Dependency Injection) — механизм, позволяющий подменять сервисы, не переписывая компоненты.

## Цель темы

**Цель:** изучить подходы к организации кода в крупных приложениях.

После изучения темы вы будете знать/уметь:

- **знать** архитектуру SPA и её преимущества перед многостраничными приложениями;
- **знать** паттерны MVC и MVVM, их различия и область применения;
- **знать** принципы разделения приложения на слои: UI, бизнес-логика, слой данных;
- **знать** структуру методологии Feature-Sliced Design: слои, слайсы, сегменты, правила импортов;
- **уметь** применять внедрение зависимостей (DI) и реализовывать простой DI-контейнер;
- **уметь** проектировать структуру каталогов фронтенд-проекта под конкретные задачи.

## Теоретическая часть

### 6.1. SPA: архитектура одностраничного приложения

**SPA (Single Page Application, одностраничное приложение)** — архитектура загрузки: браузер один раз получает HTML-оболочку, дальше маршрутизация, данные и перерисовка идут на стороне JavaScript без перезагрузки страницы.

#### Как работает SPA

При первом открытии страницы браузер загружает:
- **HTML-оболочку** — минимальная разметка с корневым контейнером (`<div id="app"></div>`)
- **JavaScript-бандл** — весь код приложения: фреймворк, компоненты, маршрутизатор, бизнес-логика
- **CSS-стили** — обычно тоже в одном или нескольких файлах

Далее приложение работает как настольная программа внутри браузера:
- **Маршрутизация** — JavaScript-роутер перехватывает клики по ссылкам и меняет URL без перезагрузки
- **Загрузка данных** — запросы к API (обычно REST через fetch/axios) за данными, а не за HTML
- **Перерисовка** — фреймворк (Vue, React, Angular) обновляет только изменившиеся части DOM

#### Сравнение с MPA (Multi-Page Application)

| Критерий | SPA | MPA (классический веб) |
| --- | --- | --- |
| Загрузка страниц | Один HTML, дальше JavaScript | Каждый переход — новый HTML с сервера |
| Скорость отклика | Быстрый (нет перезагрузок) | Медленнее (каждый переход — полная загрузка) |
| Первая загрузка | Тяжелее (нужно загрузить весь JS) | Легче (только текущая страница) |
| SEO | Требует SSR/SSG (тема 8) | Из коробки хороший |
| Сложность разработки | Выше (нужен фреймворк) | Ниже (серверный рендеринг) |
| Богатство интерфейса | Высокое (как настольное приложение) | Ограниченное (каждая форма — отдельная страница) |

#### Когда выбирать SPA

**Выбирайте SPA, когда:**
- Приложение — это инструмент, а не контент (дашборды, редакторы, CRM)
- Пользователь проводит в приложении много времени и важна скорость отклика
- Нужен сложный интерактивный интерфейс (drag-and-drop, модальные окна, обновления в реальном времени)
- Команда готова использовать фреймворк (Vue, React, Angular)

**Не выбирайте SPA, когда:**
- Сайт контентный (блог, новости, лендинг) — важен SEO и быстрая первая загрузка
- Команда не знает фреймворков и проект простой
- Нужна максимальная доступность без JavaScript

#### Архитектурные следствия SPA

SPA диктует три требования к архитектуре:

1. **Клиентская маршрутизация** — нужен роутер, который связывает URL с компонентами (Vue Router — тема 10)
2. **Управление состоянием** — данные живут в памяти браузера, нужно централизованное хранилище (Pinia — тема 10)
3. **Разделение кода** — когда весь код в одном бандле, он становится неуправляемым; нужны слои и модули (об этом дальше)

Эти три следствия и определяют архитектуру современного фронтенда — ей посвящены следующие разделы.

### 6.2. Паттерны MVC и MVVM: от классики к реактивности

Прежде чем погружаться в слои и FSD, разберём два классических архитектурных паттерна, которые определяют, как организовать связь между данными и интерфейсом.

#### MVC: Model-View-Controller

**MVC** — паттерн, пришедший из мира настольных приложений (Smalltalk, 1979). Три компонента:

- **Model (модель)** — данные и бизнес-логика. Модель знает всё о предметной области, но ничего не знает об интерфейсе.
- **View (представление)** — то, что видит пользователь: кнопки, формы, текст. View пассивно — не принимает решений, только отображает.
- **Controller (контроллер)** — посредник: принимает ввод от пользователя, обрабатывает его (или делегирует модели), обновляет View.

**Поток данных в MVC:**
1. Пользователь кликает кнопку → Controller получает событие
2. Controller обновляет Model (например, сохраняет задачу)
3. Model уведомляет View об изменении → View перерисовывается

**Пример на псевдокоде:**
```ts
// Model
class TaskModel {
  tasks: Task[] = [];
  
  addTask(title: string) {
    this.tasks.push({ title, done: false });
    this.notify(); // уведомляем View
  }
}

// View
class TaskView {
  render(tasks: Task[]) {
    // отрисовка списка задач
  }
}

// Controller
class TaskController {
  constructor(private model: TaskModel, private view: TaskView) {
    this.model.on('change', () => this.view.render(this.model.tasks));
  }
  
  onAddButtonClick(title: string) {
    this.model.addTask(title);
  }
}
```

**Где встречается:** классический веб (Ruby on Rails, Django), бэкенд-фреймворки, настольные приложения.

#### MVVM: Model-View-ViewModel

**MVVM** — эволюция MVC для мира реактивных интерфейсов (Microsoft, 2005, WPF). Три компонента:

- **Model (модель)** — данные и бизнес-логика (как в MVC)
- **View (представление)** — разметка и стили (как в MVC)
- **ViewModel (модель представления)** — *активный посредник*: хранит состояние View, реагирует на действия пользователя, автоматически синхронизируется с Model

**Ключевое отличие от MVC:** ViewModel не просто передаёт данные — она *реактивна*. Изменение в Model автоматически обновляет ViewModel, а та — View. И наоборот: действия во View (клик, ввод) автоматически вызывают методы ViewModel.

**Пример на псевдокоде (Vue 3):**
```vue
<script setup lang="ts">
// ViewModel (Composition API)
import { ref, computed } from 'vue';

const tasks = ref<Task[]>([]); // реактивное состояние

const completedCount = computed(() => 
  tasks.value.filter(t => t.done).length
); // автоматически пересчитывается

function addTask(title: string) {
  tasks.value.push({ title, done: false });
  // View обновится автоматически — не нужно вызывать render()
}
</script>

<template>
  <!-- View -->
  <div>
    <input @keyup.enter="addTask" placeholder="Новая задача" />
    <ul>
      <li v-for="task in tasks" :key="task.title">{{ task.title }}</li>
    </ul>
    <p>Выполнено: {{ completedCount }}</p>
  </div>
</template>
```

**Где встречается:** Vue, Angular, Knockout.js, WPF, Xamarin.

#### Сравнение MVC и MVVM

| Аспект | MVC | MVVM |
| --- | --- | --- |
| Роль посредника | Controller (пассивный, обрабатывает события) | ViewModel (активный, реактивный) |
| Связь View ↔ Model | Через Controller, ручное обновление | Автоматическая синхронизация (data binding) |
| Обновление View | Явное (Controller вызывает render) | Неявное (реактивность) |
| Тестируемость | Controller тестируется с моками View | ViewModel тестируется без View (чистый TypeScript) |
| Сложность | Ниже (понятный поток данных) | Выше (нужно понимать реактивность) |
| Область применения | Бэкенд, классический веб | Современные SPA-фреймворки |

#### Почему MVVM важен для Vue 3

Vue 3 построен на MVVM:
- **Model** — ваши данные (ref, reactive)
- **View** — шаблон `<template>`
- **ViewModel** — Composition API (`<script setup>`), который связывает Model и View через реактивность

Когда вы пишете `const count = ref(0)` и используете `count` в шаблоне, Vue автоматически синхронизирует их. Это и есть MVVM в действии.

Понимание MVVM критично, потому что:
1. **Компоненты Vue — это ViewModel.** Каждый `<script setup>` хранит состояние и методы, которые View использует реактивно.
2. **Props и emits — это контракт между ViewModel и View.** Props — входные данные, emits — события от View.
3. **Reactivity API (ref, reactive, computed) — это механизм связывания.** Без понимания реактивности нельзя писать на Vue.

> 💡 Полезно знать: если вы писали на jQuery («найди элемент, обнови текст»), MVVM потребует перестройки мышления. Вместо «обнови DOM вручную» вы говорите «вот состояние, фреймворк сам обновит DOM». Это называется *декларативный подход* — и он лежит в основе Vue, React и Angular.

### 6.3. Слои приложения: UI, бизнес-логика, слой данных

Воспользуемся аналогией с рестораном:

- **UI (зал)** — то, что видит посетитель: компоненты, разметка, стили, реакции на действия.
- **Бизнес-логика (кухня)** — правила предметной области: как задача меняет статус, что считается просроченным дедлайном, можно ли перенести задачу в «Готово» без исполнителя.
- **Слой данных (склад и поставщики)** — API-клиенты, хранилища, кэши: всё, что добывает и сохраняет информацию.

Правило здорового ресторана: официант не ходит на склад, склад не готовит блюда, кухня не общается с гостями напрямую. Каждый слой делает своё и общается с соседями через понятные интерфейсы.

Формальнее это описывается двумя понятиями:

- **Связность (cohesion)** — насколько модуль занят одной задачей. Высокая связность: модуль `task-deadline` делает только дедлайны.
- **Зацепление (coupling)** — насколько модули знают друг о друге. Низкое зацепление: модуль знает о соседе только через интерфейс, а не через внутренности.

Правило зависимостей формулируется просто: **зависимости направлены вниз, к абстракциям**. UI зависит от бизнес-логики, бизнес-логика — от интерфейсов слоя данных, а конкретные реализации (fetch-клиент, localStorage, файл) подключаются снаружи.

Сравним два варианта одного и того же компонента:

```ts
// ❌ Плохо: компонент сам лезет в сеть и сам решает бизнес-правила
async function completeTask(taskId: string) {
  const res = await fetch(`/api/tasks/${taskId}`, { method: 'PATCH' });
  if (res.ok) {
    const task = await res.json();
    if (task.assignee === null) {
      alert('Нельзя завершить задачу без исполнителя!');
    }
  }
}

```

```ts
// ✅ Хорошо: компонент выражает намерение, правила живут в сервисе
import { useCompleteTask } from '@/features/task-complete';

const completeTask = useCompleteTask();
await completeTask.execute(taskId); // ошибки и правила обработает слой выше
```

Во втором варианте компонент не знает, куда идёт запрос и какие правила сработают. Его можно перерисовать, перенести в мобильную сборку и протестировать, не поднимая сеть.

> 💡 Полезно знать: бизнес-логику стоит писать так, чтобы она не импортировала ничего платформенного — ни фреймворка, ни `window`, ни `localStorage`. Чистый TypeScript тестируется за миллисекунды и переживает смену фреймворка. Это называется framework-agnostic (независимый от фреймворка) код.

### 6.4. Внедрение зависимостей (Dependency Injection)

Посмотрим на сервис из «плохого» мира:

```ts
class AuthService {
  private readonly http = new FetchHttpClient('/api');     // приклеен намертво
  private readonly tokens = new LocalStorageTokenStorage(); // тоже приклеен
}
```

Этот сервис невозможно протестировать без сети и без браузера: обе зависимости создаются внутри. Внедрение зависимостей (Dependency Injection, DI) разворачивает ситуацию: **зависимости передаются объекту извне, а не создаются внутри него**.

```ts
class AuthService {
  constructor(
    private readonly http: HttpClient,       // интерфейс, а не конкретный класс
    private readonly tokens: TokenStorage,   // интерфейс, а не localStorage
  ) {}
}

// Где-то снаружи (в «корне композиции») решаем, что именно внедряем:
const authService = new AuthService(new FetchHttpClient('/api'), new BrowserTokenStorage());
```

Что это даёт фронтенду:

1. **Тестируемость.** В тестах подменяем `HttpClient` на мок — и проверяем логику без сети.
2. **Платформенная гибкость.** Помним абстракцию хранилища из темы 5: тот же `AuthService` в Node.js получит файловое хранилище, в WebView — нативное, в браузере — `localStorage`. Сервис не заметит подмены.
3. **Контроль жизненного цикла.** Контейнер создаёт сервисы один раз (singleton) и лениво — только когда их впервые запросили.
4. **Компоненты становятся потребителями, а не сборщиками.** Компоненту не нужно знать, как собрать сервис из трёх частей, — он запрашивает готовый. Конкретный механизм предоставления зависимостей компонентам зависит от выбранного UI-фреймворка.

### 6.5. Feature-Sliced Design: слои, слайсы, сегменты

Feature-Sliced Design (FSD) — открытая методология архитектурного проектирования фронтенд-приложений. Её словарь состоит из трёх понятий.

**Слои (layers)** — семь уровней, сверху вниз:

| Слой | Назначение |
| --- | --- |
| `app` | Инициализация приложения: контейнер DI, роутер, глобальные стили |
| `pages` | Целые страницы-маршруты: `pages/board`, `pages/login` |
| `widgets` | Крупные самодостаточные блоки: `widgets/kanban-board` |
| `features` | Законченные действия пользователя: `features/task-move`, `features/task-create` |
| `entities` | Бизнес-сущности: `entities/task`, `entities/project`, `entities/user` |
| `shared` | Переиспользуемый код без бизнес-логики: `shared/api`, `shared/ui`, `shared/lib` |

(Исторический слой `processes` считается устаревшим и в новых проектах не используется.)

**Слайсы (slices)** — нарезка слоя по предметной области. На слоях `pages`–`entities` каждый слайс — своя область: `entities/task`, `entities/project`... Слайс `shared` не нарезается.

**Сегменты (segments)** — нарезка слайса по техническому признаку: `ui` (компоненты), `model` (типы, состояние, бизнес-правила), `api` (запросы), `lib` (утилиты), `config` (флаги).

Два правила, на которых держится FSD:

1. **Импорты — только сверху вниз.** Слой может зависеть только от слоёв ниже. Страница импортирует виджеты и фичи, фичи — сущности, сущности — shared. Обратные импорты запрещены.
2. **Кросс-импорты между слайсами одного слоя запрещены.** `features/task-move` не импортирует `features/task-edit` напрямую. Общение между слайсами идёт через вышестоящий слой (виджет или страницу) либо через публичный API нижних слоёв.

Каждый слайс exposes свой **публичный API (public API)** — файл `index.ts`, в котором объявлено, что разрешено использовать снаружи:

```ts
// src/entities/task/index.ts — публичный API слайса
export { TaskCard } from './ui/TaskCard';
export type { Task, TaskStatus } from './model/types';
export { isOverdue } from './model/is-overdue';
```

Внутренности слайса (`model/helpers.ts`, `ui/TaskCardHeader.tsx`) снаружи невидимы. Как меню ресторана: вы заказываете блюдо, а не «вот тот соус со второй полки».

**FSD против Clean Architecture.** «Чистая архитектура» (Clean Architecture) Роберта Мартина строит систему вокруг ядра — домена (domain), с правилом зависимостей, направленным внутрь. FSD — фронтенд-специфичная адаптация похожих идей, но с центром тяжести на пользовательских сценариях (features), а не на доменных моделях, и с готовым словаром для интерфейсных проектов.

| Аспект | Clean Architecture | Feature-Sliced Design |
| --- | --- | --- |
| Центр системы | Домен (бизнес-правила) | Пользовательские сценарии (фичи) |
| Словарь | Entities, use cases, controllers | app, pages, widgets, features, entities, shared |
| Область рождения | Бэкенд, общая инженерия | Фронтенд |
| Правило зависимостей | Внутрь, к домену | Сверху вниз, по слоям |

> ⚠️ Частая ошибка: применять FSD к приложению из пяти экранов. Методология оплачивает себя в средних и крупных проектах; в маленьких достаточно здравого смысла и разделения на `shared`/`features`. Инструмент хорош, когда есть что структурировать.

> 💡 Полезно знать: главная ценность FSD — не папки, а общий язык команды. Когда разработчик говорит «это надо вынести в фичу», все понимают, куда именно и с какими правилами импорта.

### 6.6. Архитектура приложения: собираем всё вместе

Сведём идеи темы в целевую схему проекта:

```text
┌────────────────────────────────────────────┐
│ UI-слой: pages, widgets, компоненты        │  Компоненты, стили, слоты
├────────────────────────────────────────────┤
│ Бизнес-логика: features, model в entities  │  Чистый TypeScript
├────────────────────────────────────────────┤
│ Слой данных: shared/api, adapters          │  HttpClient, Storage
└────────────────────────────────────────────┘
      ↑ реализации подставляются через DI-контейнер (app)
```

## Типичные ошибки и заблуждения

1. **«Разложим по типам: components, utils, api».** Структура «по типам файлов» масштабируется до первой дюжины модулей, после чего превращается в свалку, где всё импортирует всё. FSD предлагает структуру по смыслу, а не по расширению.
2. **Кросс-импорты слайсов одного слоя.** `features/task-move` тянет код из `features/task-edit` «временно» — и через полгода две фичи нельзя удалить по отдельности. Общие куски выноите вниз, в entities или shared.
3. **Бизнес-логика в компонентах.** Компонент, который сам считает просрочку и сам ходит в сеть, невозможно протестировать без монтирования и перенести в другую платформу. Правилам — model, запросам — api, компоненту — разметка.
4. **DI «на всякий случай».** Контейнер полезен для сервисов с вариантами реализаций (API, хранилище, аналитика). Оборачивать в него каждую утилиту форматирования даты — бюрократия дороже пользы.
5. **Путаница MVC и MVVM.** В MVC Controller пассивен и обрабатывает события, в MVVM ViewModel реактивна и автоматически синхронизируется с View. Нельзя писать на Vue, думая в терминах MVC — фреймворк требует декларативного подхода.
