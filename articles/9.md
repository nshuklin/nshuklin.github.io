# Тема 09. Vue Composition API и переиспользуемые composables


## Аннотация

Composition API раскрывается по-настоящему, когда логику нужно вынести из компонента и переиспользовать. В этой теме мы углубимся в производные данные (`computed`), наблюдателей (`watch`, `watchEffect`) и главное переиспользуемое «строительное изделие» Vue — composables: функции, которые уносят с собой состояние, подписки и жизненный цикл. Попутно разберём, откуда берутся утечки памяти и как `onScopeDispose` помогает убирать за собой. На практике напишем три composables (`useDebounce`, `useBreakpoints`, `useMouse`) и подключим их к проекту.

## Цель темы

**Цель:** научиться выносить логику из компонентов для переиспользования.

После изучения темы вы будете знать/уметь:

- знать, как устроены `computed` (кэширование, ленивое вычисление) и наблюдатели `watch`/`watchEffect`;
- знать паттерны проектирования composables: состояние, аргументы-refs, возврат refs;
- уметь выносить реактивную логику в функции `useX` и подключать их в компоненты;
- уметь управлять жизненным циклом внутри composables и гарантировать очистку подписок;
- уметь диагностировать типовые ошибки: «зависимости не собираются», «значения не обновляются», утечки слушателей.

## Теоретическая часть

### 9.1. Что такое composable и зачем он нужен

Composable (переиспользуемая функция состояния) — это функция, которая инкапсулирует реактивное состояние, логику и (опционально) подписки на события/жизненный цикл, и может вызываться из setup любого компонента. Соглашение именования — префикс `use`: `useMouse`, `useDebounce`, `useTaskFilter`.

Сравним способы переиспользования логики во Vue:

| Механизм | Что переиспользует | Недостатки |
|---|---|---|
| миксин (mixin, Options API) | объект опций, подмешивается к компоненту | неявные свойства, конфликты имён, непонятно, откуда что пришло |
| компонент | UI + логика вместе | привязан к разметке, сложен для «чистой» логики |
| обычная функция | чистую логику | не умеет в реактивность и жизненный цикл |
| **composable** | **состояние + логику + подписки** | — (стандарт современного Vue) |

Простейший пример — composable, считающий количество выполненных задач:

```ts
// src/composables/useDoneCount.ts
import { computed, type Ref } from 'vue'
import type { Task } from '@/types/task'

export function useDoneCount(tasks: Ref<Task[]>) {
  const doneCount = computed(() => tasks.value.filter((t) => t.status === 'done').length)
  const progress = computed(() =>
    tasks.value.length === 0 ? 0 : Math.round((doneCount.value / tasks.value.length) * 100),
  )
  return { doneCount, progress }
}
```

```vue
<script setup lang="ts">
const { doneCount, progress } = useDoneCount(tasks)
</script>
```

Composable — это не «магия фреймворка», а обычная функция. Но вызванная в правильном месте (в setup-контексте компонента), она получает суперспособности: доступ к реактивной системе и хукам жизненного цикла текущего компонента.

### 9.2. `computed`: производные данные с кэшем

Вычислимое свойство (computed property) — реактивное значение, которое выводится из других реактивных значений:

```ts
import { computed, ref } from 'vue'

const filter = ref<'все' | 'активные' | 'готово'>('все')
const tasks = ref<Task[]>([])

const visibleTasks = computed(() => {
  if (filter.value === 'все') return tasks.value
  const status = filter.value === 'готово' ? 'done' : 'todo'
  return tasks.value.filter((t) => t.status === status)
})
```

Ключевые свойства `computed`:

1. **Ленивость (lazy).** Функция не выполняется при создании — только при первом чтении `.value`.
2. **Кэширование.** Пока зависимости не менялись, повторные чтения возвращают кэш без пересчёта. Если `visibleTasks` в шаблоне читается пять раз, фильтр отработает один.
3. **Автотрекинг зависимостей.** Зависимости собираются динамически во время выполнения: какие свойства прочитаны в функции — те и отслеживаются (вспоминаем `track` из темы 9).
4. **Чистота.** Внутри `computed` нельзя делать побочные эффекты: ни запросов, ни `console.log` «для отладки», ни мутаций чужого состояния. `computed` отвечает на вопрос «чему равно?», а не «что сделать?».

Существует и перезаписываемый `computed` с объектом `{ get, set }` — редкий, но полезный приём:

```ts
const allDone = computed({
  get: () => tasks.value.length > 0 && tasks.value.every((t) => t.status === 'done'),
  set: (value: boolean) => {
    tasks.value.forEach((t) => { t.status = value ? 'done' : 'todo' })
  },
})
```

### 9.3. `watch` и `watchEffect`: наблюдатели

Когда нужно не вычислить значение, а **отреагировать** на изменение — выполнить побочный эффект (запрос к серверу, запись в хранилище, логирование), — используют наблюдателей (watchers).

**`watch(source, callback, options?)`** следит за явно указанным источником:

```ts
import { watch } from 'vue'

watch(searchQuery, async (newValue, oldValue) => {
  if (newValue === oldValue) return
  results.value = await api.searchTasks(newValue)
})
```

Источником может быть ref, геттер `() => obj.field` или массив источников. Опции:

| Опция | Что делает |
|---|---|
| `immediate: true` | колбэк выполняется сразу при создании наблюдателя |
| `deep: true` | обходит вложенные объекты (осторожно: дорого на больших структурах) |
| `once: true` | срабатывает один раз и отключается |
| `flush: 'post'` | выполняется после обновления DOM (когда нужен свежий DOM) |

Отдельная важная возможность — **очистка асинхронной работы**. Если пользователь печатает быстро, устаревший запрос нужно отменить:

```ts
watch(searchQuery, (query, _old, onCleanup) => {
  const controller = new AbortController()
  loadResults(query, controller.signal)
  onCleanup(() => controller.abort()) // вызовется перед следующим запуском и при остановке
})
```

**`watchEffect(callback)`** не спрашивает, за чем следить, — он выясняет это сам, выполняя колбэк и собирая все прочитанные реактивные зависимости:

```ts
watchEffect(() => {
  // зависимость — всё, что прочитано синхронно внутри:
  document.title = `My App: ${visibleTasks.value.length} задач`
})
```

Сравним наблюдателей:

| Критерий | `watch` | `watchEffect` |
|---|---|---|
| Источник | указывается явно | собирается автоматически |
| Старое значение | доступно как аргумент | недоступно |
| Первый запуск | по желанию (`immediate`) | всегда сразу |
| Когда предпочитать | точечная реакция на конкретное значение | эффект зависит от многих значений сразу |

> ⚠️ Классическая ловушка `watchEffect` и async: зависимости собираются только в **синхронной** части колбэка. Всё, что прочитано после первого `await`, реактивная система уже не видит. Нужен контроль над источником — берите `watch`.

> 💡 Правило выбора: если результатом должно быть **значение** — это `computed`; если результатом должно быть **действие** — это `watch`. `computed` с побочными эффектами внутри — примета будущего бага.

### 9.4. Паттерны написания composables

Несколько правил, которые отличают аккуратный composable от «вынесенного куска компонента»:

**1. Имя и сигнатура.** Префикс `use`, осмысленные аргументы. Если аргумент может быть как статическим значением, так и ref, принимают `MaybeRef<T>` (`T | Ref<T>`) и разворачивают через `toValue()`:

```ts
import { toValue, type MaybeRef } from 'vue'

export function useGreeting(name: MaybeRef<string>) {
  const greeting = computed(() => `Привет, ${toValue(name)}!`)
  return { greeting }
}
```

**2. Возвращайте refs, а не простые значения.** Вызывающий компонент деструктуризирует результат — если вернуть просто `number`, реактивность исчезнет (привет, тема 9). Возвращайте объект refs или единый `reactive`-объект:

```ts
export function useTaskFilter(tasks: Ref<Task[]>) {
  const query = ref('')
  const debouncedQuery = useDebounce(query, 300) // composable использует composable
  const filtered = computed(() =>
    tasks.value.filter((t) => t.title.toLowerCase().includes(debouncedQuery.value.toLowerCase())),
  )
  return { query, filtered }
}
```

**3. Stateful vs stateless.** Composable без внутреннего состояния (`useGreeting`) — чистая фабрика вычислений. Composable с состоянием (`useMouse`, `useTaskFilter`) создаёт его при каждом вызове — каждый вызвавший компонент получает свой экземпляр. Если нужно общее состояние для всего приложения (тема, например, «корзина»), состояние выносят в модуль-синглтон или стор (тема 10).

**4. Не создавайте подписки на верхнем уровне модуля.** Слушатель, добавленный при импорте файла, невозможно снять — это утечка на всё время жизни вкладки. Подписки живут внутри функции и снимаются при остановке области эффектов.

**5. Composables компонуются.** `useTaskFilter` использует `useDebounce` — это нормально и поощряется. Маленькие composables складываются в крупные, как функции в функциональном программировании.

### 9.5. Жизненный цикл внутри composables

Хуки `onMounted`, `onUnmounted` и прочие можно вызывать не только в компоненте, но и внутри composable — при условии, что composable вызывается синхронно во время setup. Vue привяжет хук к текущему компоненту:

```ts
import { onMounted, onScopeDispose, ref } from 'vue'

export function useMouse() {
  const x = ref(0)
  const y = ref(0)

  const update = (e: PointerEvent): void => {
    x.value = e.clientX
    y.value = e.clientY
  }

  onMounted(() => window.addEventListener('pointermove', update))
  onScopeDispose(() => window.removeEventListener('pointermove', update))

  return { x, y }
}
```

Здесь появляется герой второго плана — **область эффектов** (effect scope). Каждый компонент создаёт свою область; `watch`, `computed` и хуки, созданные внутри setup, принадлежат ей. Когда компонент размонтируется, Vue останавливает всю область разом. Хук `onScopeDispose` регистрирует колбэк очистки именно в этой области и работает и в composables, и во вложенных областях — это самый надёжный способ «убрать за собой».

| Ситуация | Чем чистить |
|---|---|
| слушатель DOM/`window` в composable | `onScopeDispose` (или `onUnmounted`) |
| таймер `setTimeout`/`setInterval` | сохранить id, `clearTimeout`/`clearInterval` в `onScopeDispose` |
| незавершённый запрос | `AbortController` + `onCleanup` в `watch` / `onScopeDispose` |
| WebSocket/EventSource | закрыть соединение в `onScopeDispose` |

> ⚠️ Утечка памяти (memory leak) во фронтенде чаще всего выглядит безобидно: компонент размонтирован, а его слушатель `mousemove` продолжает жить на `window`, держит замыкание и обновляет ref, который уже никто не читает. Десять открытых-закрытых страниц — и в памяти живёт десять «призрачных» обработчиков.

> 💡 Библиотека VueUse (<https://vueuse.org/>) — сотни готовых composables на все случаи жизни. Прежде чем писать свой `useStorage` или `useEventListener`, посмотрите, нет ли его там; код VueUse — отличный учебник по паттернам этой темы.

## Типичные ошибки и заблуждения

1. **Побочные эффекты в `computed`** — запросы и запись в хранилище внутри геттера. `computed` может выполняться многократно и в неожиданные моменты; действия выносите в `watch`.
2. **Зависимости `watchEffect` после `await`** — реактивная система собирает зависимости только в синхронной части колбэка; прочитанное после `await` не отслеживается.
3. **Composable возвращает «голые» значения.** После деструктуризации реактивность теряется; возвращайте refs или `reactive`-объект.
4. **Подписка без отписки** — слушатели и таймеры без `onScopeDispose`/`onUnmounted` превращают SPA в склад «призрачных» обработчиков.
5. **Вызов composable из обработчика события или условно** — хуки жизненного цикла должны регистрироваться синхронно во время setup, иначе Vue не знает, к какому компоненту их привязать.
