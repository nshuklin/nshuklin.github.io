# Тема 1. Введение в кроссплатформенную разработку

## Аннотация

Мы разберём, почему индустрия вообще пришла к идее «пиши один раз — запускай везде», проследим эволюцию подходов от нативной разработки через гибридные WebView-обёртки к кросс-компилируемым фреймворкам, заглянем внутрь WebView и поймём, почему JavaScript стал языком-посредником (lingua franca) между всеми платформами. Завершается тема практической настройкой окружения и упаковкой первой веб-страницы в настольное приложение.

## Цель темы

**Цель:** понять ландшафт кроссплатформенной разработки и место JS/веба в нём.

После изучения темы вы будете знать/уметь:

1. **знать** три поколения кроссплатформенных подходов (нативный, гибридный, кросс-компилируемый) и их принципиальные отличия;
2. **знать** архитектуру WebView: как веб-страница живёт внутри нативного приложения и через что она общается с операционной системой;
3. **уметь** по косвенным признакам определять технологический стек существующих приложений;
4. **уметь** настраивать базовое окружение разработчика (Node.js, редактор, git) и проверять его работоспособность;
5. **уметь** запускать простейшее веб-приложение и оборачивать его в WebView-контейнер для десктопа.

## Теоретическая часть

### 1.1. Зачем нужна кроссплатформа: одно приложение — много экранов

Посмотрим на типичный продукт 2020-х годов. У банка есть сайт, мобильное приложение для iOS, мобильное приложение для Android, иногда десктопный клиент и умные часы. Каждая из этих площадок — отдельный пользователь, отдельный канал продаж и отдельный пункт в отчёте «почему релиз опять перенесли».

Наивное решение — писать каждую платформу отдельно: Swift для iOS, Kotlin для Android, C++/Qt или Electron для десктопа. Это работает, но у такого решения есть цена, и она измеряется не только деньгами:

| Проблема нативного мультиплатформенного подхода | Суть |
| --- | --- |
| Команды | вместо одной команды — три-четыре, со своими процессами и своим мнением о том, как должна выглядеть кнопка |
| Синхронизация фич | функция выходит на iOS в марте, на Android в мае, а на десктопе «после рефакторинга» |
| Найм | найти трёх узких специалистов сложнее и дороже, чем одного широкого |
| Тестирование | каждый баг нужно воспроизвести и проверить в трёх окружениях |

Кроссплатформенная разработка (cross-platform development) — это семейство подходов, при которых **один и тот же код (или его большая часть) используется для нескольких платформ**. Идея стара как сама индустрия: ещё в 1995-м Java обещала «write once, run anywhere», и с тех пор каждая эпоха переизобретала эту мечту с новым синтаксисом.

Важно зафиксировать ожидания сразу: кроссплатформа — это не бесплатная телепортация кода во все Вселенные, а **инженерный компромисс**. Мы платим чем-то (производительностью, доступом к экзотическим API, размером приложения) за экономию на разработке. Весь дальнейший курс — это, по сути, изучение того, чем именно платит выбранный нами стек и как сделать эту плату минимальной.

> 💡 Полезно знать: по данным опросов Stack Overflow Developer Survey, JavaScript много лет подряд остаётся самым используемым языком программирования, а среди кроссплатформенных фреймворков стабильно лидируют React Native и Flutter. То есть «кроссплатформа» — давно не нишевая история, а мейнстрим.

### 1.2. Эволюция подходов: Native, PWA, Hybrid, Cross-compiled

Исторически выделяют три поколения подходов. Разберём каждое.

#### Нативная разработка (Native)

Нативное приложение (native app) пишется на «родном» языке платформы и использует её штатные средства UI:

- iOS — Swift (ранее Objective-C), фреймворки UIKit / SwiftUI;
- Android — Kotlin (ранее Java), Android SDK с View или Jetpack Compose;
- Windows — C++/C# (WinUI, WPF), macOS — Swift/AppKit.

**Плюсы:** максимальная производительность, полный доступ ко всем API устройства, «родное» поведение интерфейса, соответствие гайдлайнам платформ.

**Минусы:** отдельная кодовая база на каждую платформу, дублирование бизнес-логики, стоимость владения растёт линейно с числом платформ.

Нативный подход никуда не делся и не денется: игры с тяжёлой графикой, системные утилиты, высоконагруженные клиенты банков часто остаются нативными. Кроссплатформа не «убила» натив — она заняла нишу продуктов, где скорость доставки фич важнее последних 5 % производительности.

#### Прогрессивные веб-приложения (PWA)

PWA берут своё начало с 2000 года, когда Microsoft стала использовать HTML-приложения в качестве справочников к своим приложениям (An HTML Application - .hta). Через 7 лет на сцену WWDC вышел Стив Джобс и сказал: "Мы нашли очень хорошее решение!" *(ориг. "very sweet solution")*, под которым он имел ввиду веб-приложения на базе Web 2.0 и AJAX. 

Однако сам термин "Progressive Web App" появился только в 2015 году — его придумали инженеры Google Алекс Рассел и Фрэнсис Берриман. Современное PWA — это, по сути, продвинутый сайт, который ведет себя как нативное приложение благодаря трем ключевым веб-стандартам: **HTTPS** (безопасность), **Web App Manifest** (JSON-файл с иконкой, именем и цветовой темой для домашнего экрана) и **Service Workers** (фоновые скрипты, позволяющие приложению работать офлайн и отправлять push-уведомления). PWA пишется на стандартных веб-технологиях (HTML, CSS, JavaScript/TypeScript) и запускается внутри браузера.

**Плюсы:**
* **Кроссплатформенность из коробки:** один и тот же код работает везде, где есть современный браузер (iOS, Android, Windows, macOS, Linux).
* **Обход App Store и Google Play:** нет комиссий (те самые 30% или 15%), нет долгих проверок (ревью) перед публикацией, нет риска внезапного бана со стороны площадки.
* **SEO и виральность:** PWA по-прежнему является сайтом. Его можно индексировать в поисковиках, а делиться им можно по обычной ссылке — пользователю не нужно переходить в стор и ждать загрузки.
* **Мгновенные обновления:** разработчик просто деплоит новую версию на сервер. Пользователю не нужно нажимать кнопку "Обновить" в сторе — при следующем открытии подтянется актуальный код.
* **Малый размер:** никаких тяжелых нативных SDK, весит буквально килобайты.

**Минусы:**
* **Ограничения iOS (Политика Apple):** Это главная боль. Apple годами искусственно урезала возможности PWA в Safari, чтобы защитить свой App Store (например, Push-уведомления для PWA на iOS появились только в 2023 году, ограничен размер кэша Service Worker, нет прямого доступа к Bluetooth, NFC или Face ID).
* **Производительность:** веб-движок (WebKit/Blink) и интерпретируемый JavaScript не могут сравниться по скорости с нативным машинным кодом (Swift, Kotlin, C++). Сложная анимация, скроллинг больших списков и тяжелые вычисления могут тормозить.
* **Слабая системная интеграция:** PWA не умеют создавать полноценные системные виджеты для домашнего экрана, не могут управлять умными часами или глубоко интегрироваться с фоновыми процессами ОС.
* **Неочевидная установка на iOS:** если на Android PWA само предлагает добавиться на рабочий стол, то в Safari на iPhone пользователю нужно самому догадаться нажать кнопку «Поделиться» -> «На экран Домой».

PWA не заменили нативные приложения, но стали индустриальным стандартом для e-commerce, медиа, сервисов бронирования (авиабилеты, отели), банковского сектора и корпоративного софта. Там, где бизнесу критически важно захватить пользователя "здесь и сейчас" (например, по клику из таргетированной рекламы или поста в соцсетях), не теряя его на этапе долгого скачивания из стора, PWA — идеальный выбор. Это современный компромисс между доступностью веба и удобством натива.

#### Гибридный подход (Hybrid)

Гибридное приложение (hybrid app) — это **нативная оболочка, внутри которой живёт веб-приложение**. Ключевой компонент здесь — WebView: специальный компонент операционной системы, представляющий собой браузер без адресной строки, встроенный прямо в приложение.

Классические представители: Apache Cordova (он же PhoneGap, 2009–2011 гг.) и Ionic. Схема работы такая:

1. вы пишете обычное веб-приложение на HTML, CSS и JavaScript;
2. сборка кладётся внутрь нативного проекта как ресурс;
3. приложение открывает его в полноэкранном WebView;
4. доступ к камере, геолокации и другим возможностям устройства предоставляется через **плагины** — мостики из JavaScript в нативный код.

**Плюсы:** одна кодовая база на все платформы, веб-разработчики могут писать мобильные приложения без изучения Swift/Kotlin, обновление контента без релиза в сторе (в ряде случаев).

**Минусы:** производительность ограничена WebView (рендеринг и исполнение JS идут через браузерный движок), интерфейс выглядит «не по-нативному», на старых Android-устройствах fragmentation версий WebView доставлял много боли.

> ⚠️ Частая ошибка: называть «гибридом» любое приложение с веб-технологиями внутри. Электронный клиент с собственным движком Chromium (Electron) и приложение на Capacitor технически тоже используют WebView/браузерный движок, но архитектурно и по экосистеме это разные классы решений. Термин «гибрид» исторически закреплён за Cordova-подобными решениями.

#### Кросс-компилируемый подход (Cross-compiled)

Кросс-компилируемые фреймворки (cross-compiled frameworks) пошли другим путём: вместо того чтобы показывать пользователю веб-страницу, они **транслируют код, написанный на одном языке, в нативные артефакты** — либо используют нативные UI-компоненты через мост, либо рисуют интерфейс собственным движком.

Два ярких представителя:

- **React Native** (Meta, 2015) — вы пишете на JavaScript/TypeScript и JSX, а фреймворк через мост (bridge, в новой архитектуре — JSI) управляет настоящими нативными компонентами платформы: `View` превращается в `UIView` на iOS и в `View` на Android.
- **Flutter** (Google, 2017) — вы пишете на языке Dart, а движок Skia/Impeller сам рисует каждый пиксель интерфейса, вообще не полагаясь на платформенные UI-компоненты.

**Плюсы:** производительность и «нативность» заметно выше гибридных решений, доступ к платформенным API, одна кодовая база.

**Минусы:** появляется промежуточный слой (мост, рантайм), который нужно понимать при отладке; Flutter требует учить новый язык (Dart); размер приложения больше, чем у чистой нативной разработки.

Сводная картина поколений:

| Критерий | Native | Hybrid | Cross-compiled |
| --- | --- | --- | --- |
| Языки | Swift/Kotlin/C++ | HTML/CSS/JS | JS/TS (React Native), Dart (Flutter) |
| Что видит пользователь | Нативные UI | Веб-страница в WebView | Нативные UI или собственный рендеринг |
| Одна кодовая база? | Нет | Да | Да |
| Производительность | Максимальная | Ограничена WebView | Близка к нативной |
| Доступ к API устройства | Полный | Через плагины | Через плагины/мост |
| Примеры | Приложение банка «изнутри» | Cordova, Ionic | React Native, Flutter |

### 1.3. Архитектура WebView

WebView заслуживает отдельного разговора, потому что именно на нём держится весь дальнейший курс: Capacitor, с которым мы будем превращать TaskFlow в мобильное приложение, — это «гибрид нового поколения», аккуратно спроектированная обёртка над WebView.

**WebView** — это компонент операционной системы, позволяющий отобразить веб-контент внутри нативного приложения. Упрощённо это браузер без интерфейса браузера: без адресной строки, вкладок и кнопок навигации.

- На Android это класс `android.webkit.WebView`, работающий на движке WebView (с версии Android 5 обновляется через Google Play как самостоятельный компонент, что заметно снизило печально известный fragmentation).
- На iOS это `WKWebView` из фреймворка WebKit — тот же движок, что и в Safari.

Архитектурно гибридное приложение похоже на матрёшку:

1. **Внешний слой** — нативное приложение, которое устанавливается из App Store / Google Play, имеет иконку, splash-экран, нативные разрешения и жизненный цикл.
2. **Средний слой** — WebView, растянутый на весь экран.
3. **Внутренний слой** — ваше веб-приложение (HTML/CSS/JS), которое может лежать в ресурсах приложения (офлайн-доступ) или загружаться по HTTPS.

Связь внутреннего слоя с внешним обеспечивает **JS-мост (JavaScript bridge)** — механизм, позволяющий JavaScript-коду вызывать нативные функции и наоборот. В Capacitor этот мост спроектирован как promisified API: из JS вы вызываете, например, `Camera.getPhoto()`, а под капотом мост передаёт вызов нативному коду и возвращает Promise с результатом.

**Ограничения WebView**, о которых нужно помнить:

1. **Производительность.** Всё исполняется внутри браузерного движка: сложная анимация, большие списки и тяжёлые вычисления могут тормозить. Часть проблем решается оптимизацией (виртуализация списков, Web Workers, GPU-ускоренные CSS-трансформации), но физику не обмануть.
2. **Ограниченный доступ к API устройства.** Камера, push-уведомления, файловая система, биометрия доступны только через мост и плагины, и только в тех пределах, в которых ОС разрешает это приложению.
3. **Песочница (sandbox).** Веб-код исполняется в изолированной среде браузера: нет прямого доступа к файловой системе ОС, к другим приложениям, к системным вызовам. Это ограничение — одновременно и главная фича безопасности.
4. **Консистентность рендеринга.** Движки на разных платформах и версиях ОС могут слегка отличаться; ваш CSS-шедевр на Android 10 и iOS 18 может выглядеть как два разных шедевра.
5. **Память и жизненный цикл.** WebView — достаточно тяжёлый объект; утечки памяти в JS-коде на мобильном устройстве чувствительнее, чем на десктопе с 32 ГБ RAM.

> 💡 Полезно знать: на десктопе ту же идею доводят до максимума Electron и Tauri. Electron упаковывает в каждое приложение полноценный Chromium и Node.js (поэтому Electron-приложения весят сотни мегабайт — вместе с ними вы скачиваете целый браузер). Tauri использует системный WebView (WebView2 на Windows, WKWebView на macOS), поэтому дистрибутив получается в разы меньше.

### 1.4. JavaScript как lingua franca кроссплатформы

Lingua franca — язык-посредник, на котором договариваются носители разных языков. В мире платформ таким посредником стал JavaScript, и это не случайность.

**Почему именно JavaScript?**

1. **Единственный язык, который исполняется во всех браузерах.** Веб-платформа — самая массовая runtime-среда в истории: миллиарды устройств, и на каждом уже есть движок JavaScript (V8 в Chrome, JavaScriptCore в Safari и т. д.).
2. **Node.js (2009) вывел JS за пределы браузера.** Серверы, CLI-инструменты, сборщики — всё это тоже JavaScript. Возникла уникальная ситуация: один язык на клиенте, сервере и в инструментах сборки.
3. **Экосистема.** npm — крупнейший реестр пакетов в мире. Любой кроссплатформенный фреймворк, выбравший JS, получает эту экосистему «в наследство».
4. **TypeScript добавил статическую типизацию.** Это сняло главный исторический аргумент скептиков («JS — для прототипов, серьёзные системы на нём не пишут»). Сегодня TypeScript — стандарт индустрии для крупных фронтенд-проектов.

Карта присутствия JS на платформах впечатляет:

| Платформа | Технология | Примеры известных продуктов |
| --- | --- | --- |
| Веб | Браузерные движки | Всё, что вы открываете по ссылке |
| Десктоп | Electron, Tauri | VS Code, Discord, Slack, Figma Desktop |
| iOS / Android | React Native, Capacitor | Discord, Shopify (React Native); множество приложений на Ionic/Capacitor |
| Сервер | Node.js | Бэкенды, API, сборщики (включая Vite, который мы будем использовать) |

Именно поэтому курс построен вокруг JS/TS: выучив один язык, вы получаете ключ одновременно к вебу, десктопу и мобильной разработке. Спойлер: даже Flutter-разработчики всё равно используют JavaScript-инструменты для CI/CD, но это уже за пределами нашего курса.

### 1.5. Сравнение современных подходов: React Native, Flutter, Capacitor, PWA

Теперь сведем к общему знаменателю четыре подхода, которые чаще всего обсуждают в 2020-х.

**React Native** — кросс-компилируемый фреймворк от Meta. Код на JS/TS управляет нативными компонентами через мост. Сильные стороны: зрелая экосистема, много готовых библиотек, JS-разработчикам вход почти бесплатный. Слабые стороны: мост — дополнительный слой абстракции, который нужно понимать; обновления фреймворка иногда болезненны.

**Flutter** — фреймворк от Google на языке Dart с собственным рендерингом. Сильные стороны: идентичный пиксель-в-пиксель интерфейс на всех платформах, отличная производительность анимаций, поддержка не только мобильных, но и десктопных сборок. Слабые стороны: отдельный язык Dart (его нужно учить с нуля), интерфейс рисуется сам — платформенные нюансы (например, поведение скролла) приходится имитировать.

**Capacitor** — преемник идей Cordova от команды Ionic: современный гибридный контейнер. Вы пишете обычное веб-приложение (в нашем случае на Vue 3), а Capacitor оборачивает его в нативные проекты для iOS и Android с аккуратным promisified-мостом и плагинами. Сильные стороны: ваш код — это просто веб-приложение (один и тот же проект работает и в браузере, и в приложении), низкий порог входа для веб-разработчиков. Слабые стороны: всё упирается в возможности WebView.

**PWA (Progressive Web App, прогрессивное веб-приложение)** — строго говоря, не фреймворк, а набор веб-технологий (Service Worker, Web App Manifest, HTTPS), который позволяет сайту вести себя как приложение: устанавливаться на устройство, работать офлайн, показывать push-уведомления. Сильные стороны: нет магазинов и модераций, мгновенное обновление, один URL для всех. Слабые стороны: ограничения браузерных API (особенно на iOS), push-уведомления и установка работают не везде одинаково.

Сравнительная таблица:

| Критерий | React Native | Flutter | Capacitor | PWA |
| --- | --- | --- | --- | --- |
| Язык | JS/TS | Dart | HTML/CSS/JS/TS | HTML/CSS/JS/TS |
| UI | Нативные компоненты | Собственный рендеринг | Веб (WebView) | Веб (браузер) |
| Веб-версия из того же кода | Нет | Частично | Да | Да (это и есть веб) |
| Установка в сторы | Да | Да | Да | Не требуется |
| Офлайн-режим | Свои решения | Свои решения | Веб-API (IndexedDB и др.) | Service Worker |
| Порог входа для веб-разработчика | Средний | Высокий (новый язык) | Низкий | Низкий |
| Производительность UI | Высокая | Высокая | Средняя | Средняя |

Вывод, который стоит запомнить: **серебряной пули нет**. Выбор определяется требованиями продукта: нужен максимальный «нативный» опыт — React Native или Flutter; команда состоит из веб-разработчиков и продукт уже живёт в браузере — Capacitor и PWA. Мы в курсе выбрали второй путь — и не только из любви к веб-платформе: это самый быстрый способ провести студента от «пишу на JS» до «моё приложение установлено на телефон».

## Типичные ошибки и заблуждения

1. **«Write once, run anywhere» = «ничего адаптировать не нужно».** Один код — не значит один интерфейс: размеры экранов, жесты, системные шрифты и гайдлайны платформ всё равно приходится учитывать. Кроссплатформа экономит бизнес-логику, а не здравый смысл.
2. **«Гибридные приложения всегда безнадежно медленные».** Современные WebView-движки быстры, а многие проблемы «тормозящих гибридов» 2015 года решаются грамотной оптимизацией (виртуализация списков, Web Workers). Медленным обычно является конкретное приложение, а не весь класс подходов.
3. **«PWA полностью заменяет нативное приложение».** PWA не имеют доступа ко многим нативным API (особенно на iOS), а установка и push работают не во всех браузерах. Для полноценного продукта PWA и нативный контейнер (Capacitor) чаще всего используются вместе.
4. **«React Native — это когда сайт открывают на телефоне».** Нет: React Native управляет настоящими нативными компонентами через мост, браузер там не участвует. Сайт внутри телефона — это гибридный подход.
5. **«Сначала выберем модный фреймворк, потом подумаем о требованиях».** Правильный порядок обратный: требования продукта и компетенции команды определяют стек, а не наоборот.
