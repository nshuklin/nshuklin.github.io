# Тема 3. Асинхронный JavaScript — Event Loop, Promise, async/await

## Аннотация

Асинхронность — то место, где JavaScript ломает интуицию, привыкшую к последовательному коду, и то же место, где рождаются самые загадочные баги пользовательских интерфейсов: «данные загрузились, но экран пустой». В этой теме мы заглянем под капот исполнения JS: разберём стек вызовов, очереди задач и механизм цикла событий (event loop), научимся строить цепочки промисов, правильно обрабатывать ошибки и выбирать паттерны конкурентного выполнения. Практика — предсказание порядка вывода, рефакторинг callback-ада в async/await и реализация параллельной загрузки данных TaskFlow.

## Цель темы

**Цель:** глубокое понимание асинхронности для предотвращения багов в UI.

После изучения темы вы будете знать/уметь:

1. **знать** модель выполнения JavaScript: стек вызовов (call stack), Web APIs, очередь макрозадач (task queue) и очередь микрозадач (microtask queue);
2. **уметь** предсказывать порядок вывода кода, в котором смешаны `setTimeout`, промисы и синхронные вызовы;
3. **знать** состояния Promise и уметь строить цепочки с корректной обработкой ошибок;
4. **уметь** переписывать callback-код в `async/await` без потери логики обработки ошибок;
5. **уметь** выбирать между последовательным и конкурентным выполнением запросов (`Promise.all`, `allSettled`, `race`, `any`).

## Теоретическая часть

### 3.1. Однопоточный JavaScript и стек вызовов

JavaScript — **однопоточный** язык: в одном движке код выполняется на одном главном потоке, а значит, в каждый момент времени исполняется ровно одна функция. Управляет этим **стек вызовов** (call stack) — структура данных, работающая по принципу LIFO («последним пришёл — первым ушёл»).

```js
function third() {
  console.log('третья');
}

function second() {
  third();
}

function first() {
  second();
}

first();
```

Что происходит в стеке: `first` кладётся в стек, затем поверх неё `second`, затем `third`. Когда `third` завершается, она снимается со стека, управление возвращается в `second`, и так далее. Пока стек не опустеет, никакой другой код выполниться не может.

Отсюда фундаментальная проблема: если функция выполняется долго (тяжёлый цикл, ожидание сети), она **блокирует** весь поток — интерфейс замирает, клики не обрабатываются. Такой код называют блокирующим, и весь дальнейший материал — это история о том, как JavaScript научился ждать, не блокируя поток.

```js
// Антипример: так делать нельзя
const response = await fetch(url); // нормальный асинхронный код...
let sum = 0;
for (let i = 0; i < 1_000_000_000; i++) sum += i; // ...который убили этим циклом
```

Ключевая идея: **асинхронность в JS — это не многопоточность**. Долгие операции не выполняются «в другом потоке JS» — они делегируются среде исполнения, а главный поток продолжает работать.

### 3.2. Web APIs и две очереди задач

Долгие операции — таймеры, сетевые запросы, события DOM, чтение файлов — берет на себя **среда исполнения**: браузер со своими Web APIs или Node.js со своими API. Схема такая:

1. ваш код вызывает `setTimeout(callback, 1000)` — и немедленно продолжает работу;
2. таймером занимается браузер (не JS-движок);
3. когда время вышло, браузер **кладёт callback в очередь задач**;
4. как только стек вызовов пуст, цикл событий достаёт callback из очереди и выполняет.

Очередей на самом деле две, и их приоритеты разные:

| Очередь | Что в неё попадает | Приоритет |
| --- | --- | --- |
| Очередь макрозадач (task queue / macrotask queue) | `setTimeout`, `setInterval`, события DOM, ввод-вывод | Обычный |
| Очередь микрозадач (microtask queue) | реакции промисов (`then`/`catch`/`finally`), `queueMicrotask`, `MutationObserver` | Повышенный |

Разберём классический пример, который обязан уметь объяснять каждый JavaScript-разработчик:

```js
console.log('1 — старт');

setTimeout(() => {
  console.log('2 — setTimeout');
}, 0);

Promise.resolve().then(() => {
  console.log('3 — промис');
});

console.log('4 — финиш');
```

Порядок вывода: **1, 4, 3, 2**. Почему?

1. `console.log('1 — старт')` выполняется синхронно немедленно.
2. `setTimeout` регистрирует таймер в Web APIs и продолжает работу (задержка 0 мс не означает «немедленно» — означает «как только дойдёт очередь макрозадач»).
3. `.then` промиса ставит колбэк в очередь **микрозадач**.
4. `console.log('4 — финиш')` выполняется синхронно.
5. Стек пуст. Цикл событий сначала полностью разбирает очередь микрозадач → печатается «3».
6. Затем берётся одна макрозадача → печатается «2».

> ⚠️ Частая ошибка: считать, что `setTimeout(fn, 0)` выполнит `fn` сразу после текущего кода. Нет: между ними могут выполниться все накопленные микрозадачи, а при занятом стеке таймер вообще подождёт. Задержка — это минимальный срок, а не точный.

> 💡 Полезно знать: в браузере между макрозадачами происходит отрисовка интерфейса (rendering). Микрозадачи такого шанса не имеют — они исполняются «залпом», до следующей макрозадачи. Отсюда правило: промисные цепочки не должны быть бесконечными, иначе интерфейс «встанет».

### 3.3. Механизм цикла событий (Event Loop)

Цикл событий (event loop) — это диспетчер, который бесконечно повторяет простой алгоритм:

1. Дождаться, пока стек вызовов опустеет.
2. Выполнить все микрозадачи, накопившиеся в очереди (включая те, что появились в процессе выполнения других микрозадач).
3. Если очередь макрозадач не пуста — взять одну макрозадачу и выполнить её.
4. Вернуться к шагу 1 (в браузере на этом же шаге при необходимости происходит отрисовка).

Метафора для запоминания: цикл событий — официант с одним подносом (стек вызовов). У него две очереди заказов: общая очередь (макрозадачи) и VIP-клиенты (микрозадачи), которых обслуживают вне очереди, пока не кончатся. Поднос при этом один: одновременно официант несёт только одно блюдо.

Несколько следствий из этого алгоритма, важных для UI:

- **Голодание макрозадач.** Если микрозадачи постоянно порождают новые микрозадачи (например, рекурсивный `Promise.resolve().then(...)`), очередь макрозадач и отрисовка не получат управления никогда. UI замрёт.
- **Таймеры — не точные часы.** `setInterval(fn, 100)` обещает «не чаще, чем раз в 100 мс», но если поток занят, интервалы растянутся.
- **Порядок важнее задержки.** Задача с большей задержкой может выполниться раньше, если попала в очередь микрозадач, а конкурент — в макрозадачи.

Инструменты для визуализации: сайт [JavaScript Visualizer 9000](https://www.jsv9000.app/) (наглядно показывает стек и очереди), а также вкладка Performance в DevTools браузера. На практике вы будете пользоваться ими не каждый день, но один раз увидеть, как это работает вживую, — бесценно.

### 3.4. Promise: состояния, цепочки, обработка ошибок

**Promise** (промис, «обещание») — объект, представляющий результат асинхронной операции, которая завершится в будущем. У промиса ровно три состояния:

| Состояние | Когда | Что хранит |
| --- | --- | --- |
| `pending` (ожидание) | операция ещё выполняется | ничего |
| `fulfilled` (выполнен успешно) | операция завершилась успешно | значение результата |
| `rejected` (отклонён) | операция завершилась ошибкой | причину ошибки |

Из `pending` промис переходит в одно из двух конечных состояний ровно один раз и навсегда (settled — «осевший»). Подписываются на результат методами `.then(onFulfilled, onRejected)`, `.catch(onRejected)` и `.finally(onFinally)`.

**Цепочки промисов** — ключевой механизм композиции. Каждый `.then` возвращает новый промис, поэтому вызовы выстраиваются в цепочку:

```js
fetch('/api/user/1')
  .then((response) => response.json())        // возвращает Promise с данными
  .then((user) => fetch(`/api/projects/${user.id}`))
  .then((response) => response.json())
  .then((projects) => {
    console.log(`Проекты пользователя: ${projects.length}`);
  })
  .catch((error) => {
    // единая точка обработки ошибок всей цепочки
    console.error('Что-то пошло не так:', error);
  })
  .finally(() => {
    hideSpinner(); // выполняется всегда: и при успехе, и при ошибке
  });
```

Правила цепочек, которые нужно запомнить:

1. Возвращённое из `.then` **значение** становится аргументом следующего `.then`.
2. Возвращённый из `.then` **промис** «пробрасывается»: следующий `.then` ждёт его результата.
3. Брошенная внутри `.then` ошибка (`throw`) превращается в `rejected` и летит до ближайшего `.catch`.
4. `.catch` можно ставить в конце цепочки — он перехватит ошибки **всех** предыдущих шагов (включая сетевые ошибки `fetch`).
5. Необработанное отклонение (`unhandledrejection`) в браузере попадёт в консоль как ошибка — в продакшене такие случаи нужно логировать.

> ⚠️ Частая ошибка: «забытый» `return` внутри `.then`. Если обработчик ничего не вернул, следующий `.then` получит `undefined`, а не данные предыдущего шага. Половина студенческих багов в цепочках выглядит именно так.

### 3.5. async/await: тот же промис, но читается как синхронный

Синтаксис `async/await` (ES2017) — это синтаксический сахар над промисами, который позволяет писать асинхронный код, визуально похожий на синхронный. Правила:

1. Функция с ключевым словом `async` всегда возвращает Promise (даже если вы вернули число).
2. `await` внутри такой функции приостанавливает её выполнение до результата промиса. Главный поток при этом не блокируется — остальные задачи исполняются.
3. Отклонённый промис в `await` бросает ошибку — её можно поймать обычным `try/catch`.

Тот же код из прошлого раздела на async/await:

```js
async function loadUserProjects(userId) {
  try {
    const response = await fetch(`/api/user/${userId}`);
    const user = await response.json();

    const projectsResponse = await fetch(`/api/projects/${user.id}`);
    const projects = await projectsResponse.json();

    return projects;
  } catch (error) {
    console.error('Что-то пошло не так:', error);
    throw error; // пробрасываем дальше, если не можем обработать
  } finally {
    hideSpinner();
  }
}
```

Сравните: логика идентична цепочке промисов, но читается сверху вниз, как обычный код, а обработка ошибок — знакомый `try/catch`.

Важные тонкости:

- `await` работает только внутри `async`-функций (и на верхнем уровне ES-модулей — top-level await).
- Каждый `await` в цепочке выполняется **последовательно**. Если запросы независимы — последовательные `await` зря ждут друг друга (см. следующий раздел).
- `async`-функция начинает выполняться синхронно до первого `await` — это иногда важно для порядка событий.

### 3.6. Паттерны конкурентного выполнения

Частый сценарий TaskFlow: открыть дашборд, для которого нужны проекты пользователя, список задач и уведомления. Три независимых запроса. Как их выполнить?

**Последовательно** (медленно):

```js
async function loadDashboardSequential(userId) {
  const projects = await fetchProjects(userId);   // ждём 300 мс
  const tasks = await fetchTasks(userId);         // потом ещё 300 мс
  const notifications = await fetchNotifications(userId); // и ещё 300 мс
  return { projects, tasks, notifications };      // итого ~900 мс
}
```

**Конкурентно** (быстро) — запросы стартуют одновременно:

```js
async function loadDashboard(userId) {
  const [projects, tasks, notifications] = await Promise.all([
    fetchProjects(userId),
    fetchTasks(userId),
    fetchNotifications(userId),
  ]);
  return { projects, tasks, notifications }; // итого ~300 мс
}
```

Разница на ровном месте — втрое. Запоминаем статические методы Promise:

| Метод | Ждёт | Результат | Поведение при ошибке |
| --- | --- | --- | --- |
| `Promise.all([...])` | успех всех | массив результатов в исходном порядке | сразу отклоняется при первой ошибке |
| `Promise.allSettled([...])` | завершение всех | массив `{ status, value/reason }` | никогда не отклоняется |
| `Promise.race([...])` | первое завершение (любой исход) | значение/ошибка первого | зависит от первого завершившегося |
| `Promise.any([...])` | первый успех | значение первого успешного | `AggregateError`, если успеха не было ни у кого |

Выбор паттерна — по смыслу задачи:

- нужны все данные и критична любая ошибка → `Promise.all`;
- нужны все результаты, но падение части допустимо (например, виджеты дашборда: один упал — остальные показываем) → `Promise.allSettled`;
- таймаут запроса: «либо ответ, либо ошибка через 5 секунд» → `Promise.race([запрос, таймаут])`;
- несколько зеркал/CDN, достаточно первого ответившего → `Promise.any`.

```js
// allSettled в деле: дашборд TaskFlow, где каждый виджет сам по себе
const results = await Promise.allSettled([
  fetchProjects(userId),
  fetchTasks(userId),
  fetchNotifications(userId),
]);

for (const result of results) {
  if (result.status === 'fulfilled') {
    renderWidget(result.value);
  } else {
    renderWidgetError(result.reason);
  }
}
```

Финальный штрих — **лимитирование параллелизма**. `Promise.all` запускает все задачи сразу; если их 500, вы положите и сервер, и браузер. В таких случаях используют ограничитель конкурентности (concurrency limiter): «выполняй задачи пачками не больше N одновременно». Именно его вы реализуете в домашнем задании — это классическая задача, которая встречается и в реальных проектах, и на собеседованиях.

### Задание 2. Рефакторинг callback-hell в async/await (~40 минут)

Дано: загрузка данных TaskFlow в стиле 2012 года — пирамида колбэков, которую в сообществе называют «адом колбэков» (callback hell).

```js
// legacy-load.js
function loadDashboard(userId, callback) {
  fetchUser(userId, (user) => {
    fetchProjects(user.id, (projects) => {
      fetchTasks(projects[0].id, (tasks) => {
        fetchNotifications(user.id, (notifications) => {
          callback(null, { user, projects, tasks, notifications });
        }, (error) => callback(error));
      }, (error) => callback(error));
    }, (error) => callback(error));
  }, (error) => callback(error));
}
```

Задание:

1. Оберните `fetchUser`, `fetchProjects`, `fetchTasks`, `fetchNotifications` в промисы (функция `promisify`, принимающая функцию с колбэком вида `(error, result) => ...`, либо перепишите их на промисы вручную — эмуляторы запросов с `setTimeout` выдаются преподавателем).
2. Перепишите `loadDashboard` через `async/await` с `try/catch`.
3. Убедитесь, что ошибка на любом уровне приводит к одному перехвату, а не к четырём.

Ожидаемый результат: плоская функция на ~15 строк с единым `try/catch`, поведение идентично исходному. Проверка: запустите с валидным и с «падающим» `userId` (эмулятор отклоняет запрос) — во втором случае ошибка должна попасть ровно в один catch.

### Задание 3. Последовательная и параллельная загрузка (~50 минут)

Реализуйте два варианта загрузки дашборда TaskFlow на эмуляторе запросов (каждый «запрос» завершается за 300 мс через `setTimeout`):

```js
// api-mock.js
const delay = (ms) => new Promise((resolve) => setTimeout(resolve, ms));

const fetchProjects = async (userId) => {
  await delay(300);
  return [{ id: 1, name: 'TaskFlow' }];
};

const fetchTasks = async (userId) => {
  await delay(300);
  return [{ id: 1, title: 'Деплой' }];
};

const fetchNotifications = async (userId) => {
  await delay(300);
  return [{ id: 1, text: 'Новая задача' }];
};

module.exports = { fetchProjects, fetchTasks, fetchNotifications };
```

1. **Последовательная** загрузка: три `await` подряд. Замерьте время через `console.time('seq')` / `console.timeEnd('seq')`.
2. **Параллельная** загрузка через `Promise.all`. Замерьте аналогично.
3. **Устойчивая** загрузка через `Promise.allSettled`: сделайте так, чтобы `fetchNotifications` отклонялся (эмулируйте сбой), и выведите статус каждого результата.

Ожидаемый результат: последовательный вариант ~900 мс, параллельный ~300 мс, вариант с `allSettled` показывает два `fulfilled` и один `rejected`, не падая целиком. Вывод зафиксируйте в отчёте.

## Типичные ошибки и заблуждения

1. **`setTimeout(fn, 0)` — значит «сразу».** Нет: сначала выполнятся синхронный код до конца стека, затем все микрозадачи, и только потом макрозадачи. Нулевая задержка — это минимальная задержка, а не гарантия мгновенности.
2. **Забытый `return` в `.then`.** Цепочка продолжает работать, но следующие обработчики получают `undefined` вместо данных. Возвращайте данные или промис из каждого обработчика.
3. **Последовательные `await` для независимых запросов.** Три `await` подряд для независимых данных суммируют задержки. Независимое — в `Promise.all`.
4. **`Promise.all` там, где допустим частичный сбой.** Одна ошибка — и всего дашборда нет. Для независимых виджетов используйте `allSettled` и показывайте то, что загрузилось.
5. **«Асинхронный = быстрый».** Асинхронность не ускоряет запросы — она не даёт им блокировать интерфейс. Тяжёлый синхронный цикл внутри `async`-функции всё так же заморозит вкладку: для вычислений есть Web Workers.
